## 二、发现的两个 Windows 真实缺陷（仅记录，未改代码）

### Bug 1：Windows 上 `psycopg 3.3.9`（libpq 180004）配合 `make_engine()` 缺省 `connect_timeout` 导致 PG 停机时 `/api/auth/me` 永久挂起（17.6 步骤 3a）
- **复现步骤**：启动后端（`docmgr_ui`）与前端，登录后停止 PostgreSQL（`127.0.0.1:55432`），保持后端运行，在文件页按 F5 刷新。
- **实测现象**：`/api/auth/me` 请求一直处于 Pending 状态超过 90 秒（测试脚本等待 25.1s 超时），既不返回 `503` 也不报错；但清空令牌直接访问 `/login` 时的 `/health` 检查（使用带超时的独立探活）在 **4.768 秒**即正确弹出 T24z“后端已启动，但数据库不可用……”提示。
- **底层定位**（见 `output/windows-w9/login/psycopg-info.txt`）：
  - 本机环境：`psycopg 3.3.9 (binary)`, `libpq 180004`。
  - Windows 原生 `socket.connect(('127.0.0.1', 55432))` 在 2.013s 报 `WinError 10061`；但 `psycopg.connect(..., connect_timeout=10)` 不会因 `WSAECONNREFUSED` 立即失败，而是持续等待直到 `connect_timeout` 到期（10.008s 报 `ConnectionTimeout`）。
  - `backend/app/db/session.py::make_engine()` 创建 SQLAlchemy 引擎时未传入 `connect_args={"connect_timeout": ...}`，在 Windows + psycopg 3.3.9 下导致连接已关闭的本地 PG 端口无限阻塞。
- **建议修复方向**（待 Barry 确认后再改）：在 `make_engine()` 中通过 `connect_args={"connect_timeout": ...}` 配置合理连接超时（如 5–10 秒）。

### Bug 2：`backend/tests/unit/test_task_errors.py::test_database_address_is_hidden` 在 Windows 失败（17.2）
- **实测现象**：`pytest` 执行时该用例失败（见 `output/windows-w9/backend.xml` / `backend-pytest.txt`）。
- **原因**：与 Bug 1 同源。测试向 `127.0.0.1:1` 发起 `connect_timeout=2` 的 `psycopg.connect`，在 Windows + psycopg 3.3.9 上触发 `ConnectionTimeout`（2 秒后抛 `connection timeout expired`），错误字符串里不包含 `"127.0.0.1"`，导致前置断言 `assert "127.0.0.1" in stored` 失败；业务函数 `public_task_error()` 脱敏逻辑本身无误。
