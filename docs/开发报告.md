## 1. 最初的预想

### 1.1 课题目标（开题报告与 GLOBAL.md v2）

做一个能在普通个人电脑上运行的文档管理系统，研究重点是**文档处理、信息检索、结果融合和系统工程实现**，模型只做推理、不训练。开题报告列出的五个目标：

1. 用户认证、权限、上传下载预览删除，数据库、磁盘、索引三者一致；
2. PDF、Word、Excel、图片的内容抽取，扫描页和图片 OCR，每段文本保留页码、段落或单元格范围；
3. 以 BM25 为基线，分别支持文件名/标签、正文、OCR 文本检索；
4. Chinese-CLIP 做自然语言到图片的检索，RRF 在文件级融合；
5. 分层查询集 + 相关性标注，做 B0–B3 对照和消融实验。

### 1.2 预定的技术方案

| 层次 | 预定方案 |
|---|---|
| 前端 | Vue 3 + TypeScript + Element Plus，PDF 用 pdf.js |
| 后端 | Python + FastAPI |
| 数据库与任务队列 | PostgreSQL，任务表 + `SELECT … FOR UPDATE SKIP LOCKED`，不用 Redis/Celery |
| 检索 | OpenSearch：`doc_meta`、`chunks` 双索引做 BM25，向量精确检索；中文分词在 smartcn 与 IK 之间实测后选定 |
| 解析 | PyMuPDF、python-docx、openpyxl |
| OCR | PaddleOCR，独立环境、独立进程 |
| 图文模型 | Chinese-CLIP，独立环境、常驻模型服务 |
| 部署 | Docker Compose（同时保留非 Docker 的说明） |

附录 A 固定了 19 项决策（A1–A19），开发全程没有修改其中任何一项（A13、A14 两项按预定流程“待实测后确定”，结果见 §4）。

### 3.2 解析、OCR 与 BM25（P1）

| 模块 | 实现内容 | 验证情况 |
|---|---|---|
| M5 解析（T09、T11） | PDF 按页抽文本并按三种情况判断是否走 OCR（D20）；Word 段落级定位；Excel 工作表 + 单元格范围；图片只做元数据；zip 炸弹防护（解压总大小、条目数、加密条目）、图片像素上限 | 本机全部通过（测试用的是现场生成的文件，没有用真实扫描件和 WPS 文件验证） |
| M7 切分（T12） | 长度、重叠可配置；PDF 页和图片不合并，Word 相邻段落、Excel 相邻行打包；`parse_version` 由算法版本、参数、解析器版本确定性算出（D25） | 本机 |
| M8 文本索引（T13） | `doc_meta`、`chunks` 两个 strict mapping，smartcn 分词，显式 BM25 参数，索引里不放权限字段；先删旧版本再写入 | Windows（OpenSearch 2.19.1 + analysis-smartcn） |

| M6 OCR Worker（T17） | 独立 ocr 环境，PP-OCRv5 mobile，常驻识别子进程（模型只加载一次），PDF 页 200 dpi 渲染，结果按“文档 + 对象”替换；T24c 起把识别参数写入 `ocr_results.params`；T24i 新增 `reocr` 命令重新识别 | 本机真实识别 4/4；Windows 全链路 |
| M11 检索 v1（T15） | 文件名/标签、正文、OCR 三路 → 聚合到 document_id（取最佳片段作证据）→ RRF → 数据库二次校验 → `SearchHit`；检索服务故障返回 503 而不是空结果；每次检索写 SearchLog | Windows（含“删除后立即查不到”“取消共享后立即查不到”） |
| M13 一致性检查（T18） | `check` 只读对账数据库、磁盘、三个索引；`repair` 必须 `--fix` 指定类别、不加 `--yes` 只演练；T21 加向量检测，T24d 加 `--force`，T24o 扩大索引结构比较范围 | Windows |

## 6. 风险与下一步

### 6.1 主要风险

1. **评测数据是关键路径。** T25–T28 和论文的实验章节都依赖它。按 A18 要分文字型、视觉型、混合型三类，视觉型查询（目标图片里没有文字）需要专门收集图片。

4. **性能数据只有组件单测。** OCR、CLIP 的耗时来自三张合成图，不能当作论文的性能结论。

1. 完成 Windows 任务书 W1（补测）和 W4（新界面联调）；联调通过后由 Barry 决定是否给 MVP-0 打 tag。
