## 1. 附录 A 的已定决策

### 1.1 数据库与任务

**A1 关系数据库使用 PostgreSQL**

- 决策：PostgreSQL 是系统唯一的关系数据库。
- 理由：它支持 `SELECT … FOR UPDATE SKIP LOCKED`，多个 Worker 可以并发领取任务而不互相阻塞，
  因此同一个数据库可以同时承担业务数据存储和任务队列两个职责。
- 代价与局限：部署时需要单独运行数据库服务，比嵌入式数据库多一个组件。

**A2 任务队列使用 PostgreSQL 任务表，不引入 Redis、Celery 等中间件**

- 决策：后台任务记录在 `processing_tasks` 表中，Worker 直接从这张表领取。
- 理由：任务状态、重试次数、失败原因与业务数据在同一个数据库、同一个事务里，
  “写入文档记录”和“创建解析任务”可以一起提交或一起回滚，不存在两个系统之间不一致的问题；系统的组件数量也最少。
- 代价与局限：Worker 靠轮询发现新任务，有秒级延迟；吞吐量受数据库限制。对单机毕业设计的规模，这两点都可以接受。

**A3 Worker 采用租约、超时回收、子进程隔离和定期重启**

- 决策：领取任务时写入租约到期时间，处理中定期续约；租约过期仍处于处理中的任务被回收。
  每个文件在子进程中处理，设超时和内存上限。Worker 处理一定数量的任务后自动退出重启。
- 理由：文档解析和 OCR 面对的是任意用户文件，可能卡死、崩溃或耗尽内存。
  租约保证 Worker 崩溃后任务不会永远停在“处理中”；子进程保证一个坏文件不会拖垮整个 Worker；
  定期重启避免长时间运行后的内存增长。
- 代价与局限：每个任务多一次启动子进程的开销；租约时长需要权衡——太短会误回收仍在正常处理的任务，太长则崩溃后恢复慢。

### 1.2 AI 组件的隔离

**A4 PaddleOCR 与 Chinese-CLIP 各用独立的虚拟环境和独立进程**

- 决策：系统使用三套 Python 虚拟环境：主环境、OCR 环境、CLIP 环境。OCR 和 CLIP 各自作为独立进程运行。
- 理由：PaddleOCR 依赖 PaddlePaddle，Chinese-CLIP 依赖 PyTorch，两套深度学习框架装在同一环境中容易产生依赖冲突。
  进程隔离还带来一个好处：任何一个 AI 组件崩溃都不影响 API 服务。
- 代价与局限：要维护三份依赖清单；进程之间只能通过数据库任务表或 HTTP 协作，不能直接调用函数。

**A5 查询文本的编码由常驻模型服务完成，调用带超时，失败即降级**

- 决策：CLIP 模型只在模型服务进程启动时加载一次。检索时 API 通过 HTTP 请求模型服务编码查询文本，
  并设置超时；超时、失败或健康检查不通过时，本次查询只使用文本通道，并在响应中标记图像通道不可用。
- 理由：模型加载耗时长，不能放在检索请求里；AI 组件故障不应影响核心的文本检索。
- 代价与局限：每次带图像通道的检索多一次本机 HTTP 调用；降级时结果不含图像通道的贡献，用户需要从响应标记中得知这一点。

### 1.3 统一单位与 ID

**A6 融合、评测、权限的统一单位是 document_id（文件级）**

- 决策：所有检索通道的结果最终都聚合到文件；RRF 融合、相关性标注、权限判断都以文件为单位。
  片段和图片只作为命中证据展示。
- 理由：文本通道返回的是片段，图像通道返回的是图片，粒度不同的结果无法直接融合；
  统一到文件之后，融合、评测和权限使用同一个单位，标注粒度也随之确定。
- 代价与局限：评测不衡量“定位到的片段是否准确”，这一点需要用来源定位准确率单独评估；
  一个很长的文件只要有一个片段相关就算命中。

**A7 确定性 ID：chunk_id = {document_id}:{parse_version}:{seq}**

- 决策：片段 ID 由文档 ID、解析版本和序号拼成，不使用随机 ID。
- 理由：同一文档用同一解析版本重新处理时，生成的 ID 完全相同，写入数据库和索引时是覆盖而不是新增，
  任务重复执行因此天然幂等。解析参数变化时 `parse_version` 随之变化，旧版本的片段可以按版本整体删除。
- 代价与局限：`parse_version` 中不能出现冒号（见 D3）。

**A15 不做文档版本管理；替换文件即新建文档**

- 决策：系统不保留文件的历史版本。要替换文件，就上传一个新文档并删除旧文档。
- 理由：一个文档永远对应一份文件内容，ID 规则和一致性设计都更简单。
- 代价与局限：替换后 `document_id` 改变，原有的共享关系和标签不会自动继承。

### 1.4 检索与索引

**A8 双索引：doc_meta（文件级）与 chunks（片段级，含 source_type）**

- 决策：文件名和标签写入文件级的 `doc_meta` 索引；正文和 OCR 文字的片段写入 `chunks` 索引，
  每个片段带 `source_type` 字段，取值为 `body`（文档自带文本）或 `ocr`（OCR 识别文字）。
- 理由：如果把文件名冗余写进每个片段，一个文件有多少片段，文件名就被重复计分多少次，片段多的长文件会被不合理地抬高。
  分成两个索引后，对照实验 B0 只查 `doc_meta`，B1 与 B2 只差一个 `source_type` 过滤条件，不需要维护多套索引。
- 代价与局限：一次检索要查两个索引，结果需要在应用层合并。

**A12 向量检索采用精确检索，权限范围作为前置过滤条件**

- 决策：图片向量检索逐一计算查询向量与候选向量的相似度，不使用 HNSW 等近似索引；
  用户可访问的文档集合作为检索前的过滤条件。
- 理由：毕业设计规模下图片数量有限，精确计算的延迟可以接受，并且省去近似索引的参数调优，实验结果也不受近似误差影响。
  权限前置过滤避免了“先取前 k 条再过滤”造成的结果数量不足。
- 代价与局限：检索延迟随图片数量线性增长。数据规模增长到延迟不可接受时需要重新评估，届时须经 Barry 确认。

**A13 中文分词方案在环境验证阶段实测确定**

- 决策：分词器不预先指定，在本机实测后确定，配置纳入版本管理。候选是官方的 analysis-smartcn 插件和社区的 IK 插件。
- 理由：OpenSearch 默认分词器把中文逐字切开，检索效果差；IK 插件必须与 OpenSearch 版本严格匹配，能否安装要实测才知道。
- 状态：**待定**，见第 2 节。

**A14 OpenSearch 降级预案：Python 端 BM25 + faiss，仅记录不实现**

- 决策：如果环境实测证明本机资源无法稳定运行 OpenSearch，备选方案是在 Python 端实现 BM25 并用 faiss 做向量检索，
  替换范围限定在检索层（M8、M10）内部。该预案只作为文档记录，不与 OpenSearch 同时实现。
- 理由：给硬件资源不足的情况留一条退路，同时避免同时维护两套检索实现。
- 状态：是否启用**待定**，见第 2 节。启用前须经 Barry 确认。

### 1.5 来源定位、删除与权限

**A9 来源定位为多态字段；Word 只定位到段落**

- 决策：来源定位按文件格式有四种形态：PDF 定位到页，Word 定位到段落序号，Excel 定位到工作表和单元格范围，图片定位到图片 ID。
- 理由：不同格式能可靠获得的位置信息不同。python-docx 读不到页码——Word 的分页是排版时才计算出来的——所以 Word 不提供页码，也不伪造。
- 代价与局限：Word 文档的检索结果不能跳转到具体页。论文中必须表述为“段落级定位”。

**A10 软删除，检索返回前用数据库二次校验**

- 决策：删除文件时先在数据库中写入删除时间，文件立即对所有查询不可见；索引和磁盘文件由后台清理任务删除。
  检索在返回结果前，用数据库校验每个候选文件，只保留未删除且当前用户有权访问的。
- 理由：搜索索引的更新是异步的，单靠索引无法保证“删除后立即搜不到”和“取消共享后立即搜不到”。
  数据库校验是这两点的唯一保证机制，因此不得以性能为由去掉。
- 代价与局限：每次检索多一次数据库查询；被过滤掉的候选会让实际返回的结果数少于请求的数量。

**A11 权限模型：owner 私有、管理员、可选的指定用户共享**

- 决策：普通用户只能访问自己上传的文档；管理员可以访问全部；owner 可以把文档共享给指定用户，被共享者获得只读和检索权限。
- 理由：满足多用户文档管理的基本需求，同时不进入部门、组织、多级权限等企业级功能。
- 代价与局限：不能按组共享，文档多时逐个共享比较繁琐。

### 1.6 范围控制

**A16 预览：PDF 用 pdf.js，图片原生显示，Word 和 Excel 展示抽取出的文本**

- 决策：只有 PDF 和图片提供原样预览；Word 和 Excel 显示系统抽取出的文本，并提供原文件下载。
- 理由：Word、Excel 的原样排版预览实质上是在线 Office，工作量大且与检索这一论文主线无关。
- 代价与局限：Word、Excel 的预览看不到原始格式、图表和公式。

**A17 图片与文档只做结构关联；文档内嵌图片的抽取归入 P4**

- 决策：系统只记录“图片属于哪个文档”。独立上传的图片本身就是一个文档；抽取 Word、PDF 内嵌的图片属于非核心增强，暂不实现。
- 理由：控制范围。自动判断“哪张图片与哪段文字语义相关”是另一个研究问题。
- 代价与局限：文档内部的插图目前不能被图像通道检索到。扫描版 PDF 的整页会做 OCR，但不做图像向量。

### 1.7 实验与开发过程

**A18 评测查询按文字型、视觉型、混合型分层；标注从阶段二起并行**

- 决策：查询集分为三类，实验结果按类别分层报告。相关性标注从阶段二开始每周进行。
- 理由：文字型查询天然有利于 BM25，视觉型查询天然有利于 CLIP；只报告总体平均值，
  结论会被查询集中各类型的比例左右。分层报告才能说明每个通道在什么情况下有贡献。
- 代价与局限：标注工作量更大；各层的查询数量较少时，指标的波动会比较大，需要如实说明。

**A19 开发按 MVP-0、MVP-1、MVP-2 分层，从数据契约和上传入库链路起步**

- 决策：先定义数据契约，再实现存储、文档管理和任务框架，然后逐层增加格式和检索通道。每一层都要求端到端可演示、有测试。
- 理由：ID 规则和任务机制是后续所有模块的基础，先定下来可以避免返工；
  分层交付保证即使时间不足，也有一个完整可用的系统，而不是多个半成品模块。

## 3. 实现过程中的决策

### D1 配置只从环境变量读取，启动时一次性校验（T01）

- 决策：后端的全部配置来自环境变量或项目根目录的 `.env` 文件。启动时检查必填项，缺失或不合法就退出，并列出出问题的变量名。
- 理由：数据库地址、密码不能散落在代码中，也不能提交到 Git；启动时就报错，比运行到一半才发现配置缺失更容易排查。
- 代价与局限：错误信息只给出变量名，不显示变量的值，因为连接串中可能带密码。

### D2 健康检查如实报告依赖状态，而不是报错（T01）

- 决策：`GET /health` 分别检查数据库、OpenSearch 和 CLIP 服务，任何一项不可用时接口仍返回 200，在响应体中标明哪一项不可用。
- 理由：CLIP 服务不可用是系统允许的正常降级状态，不应让健康检查失败；三项分开报告才能看出是哪个组件出了问题。

### D3 parse_version 只允许字母、数字、点、下划线和连字符（T02）

- 决策：`parse_version` 的字符集受限，不能包含冒号。
- 理由：`chunk_id` 用冒号分隔三段（A7），`parse_version` 中出现冒号会使 ID 无法可靠地拆回各部分。

### D4 ParsedDocument 不包含 document_id（T02）

- 决策：解析结果中没有文档 ID，文档 ID 在切分阶段由调用方传入。
- 理由：解析器是“文件路径 → 解析结果”的纯函数，不需要知道文件在系统中的身份，因此可以脱离数据库和 Web 系统单独测试。

### D5 契约对象不可修改，且禁止多余字段（T02）

- 决策：所有数据契约对象创建后不能修改字段；传入契约中没有定义的字段会报错。
- 理由：契约对象在模块之间传递，不可修改可以排除“某个模块悄悄改了数据”这类问题；
  禁止多余字段可以让字段名的拼写错误立即暴露，而不是被忽略。

### D6 ID 只接受一种写法（T02）

- 决策：解析 `chunk_id`、`image_id` 时，UUID 必须是标准小写形式，数字不能带前导零或正负号。
- 理由：数据库主键和索引文档 ID 都是按字符串比较的。如果同一个对象可以有多种写法，覆盖写入就会变成新增，幂等性失效。

### D7 枚举用字符串加 CHECK 约束，不用数据库的 ENUM 类型（T03）

- 决策：状态、角色、`source_type` 等字段在数据库中是字符串列，用 CHECK 约束限定取值。
- 理由：PostgreSQL 的 ENUM 类型增减取值需要专门的迁移操作，且不易回退；CHECK 约束只需修改约束本身。
- 代价与局限：取值在模型代码和迁移脚本中各出现一次，修改时两处都要改（有测试比对模型与迁移是否一致）。

### D8 文档处理状态与任务状态使用相同的四个取值（T03）

- 决策：`documents.status` 取 `pending`、`processing`、`succeeded`、`failed`，与任务状态一致。
- 理由：用户在文件列表中看到的状态与后台任务的状态对应，不需要另一套状态映射。
- 代价与局限：一个文档可能有多个任务（解析、OCR、向量），文档状态如何由多个任务的状态汇总，要在 T14 解析流水线中明确。

### D9 片段正文保存在数据库中（T03）

- 决策：`document_chunks` 表保存每个片段的完整文本，而不是只保存在搜索索引里。
- 理由：Word、Excel 的预览要显示抽取出的文本；索引丢失或需要更换分词器时，可以直接从数据库重建，不必重新解析和 OCR。
- 代价与局限：文本在数据库和索引中各存一份，占用更多磁盘。

### D10 图片向量保存在数据库中，按内容哈希去重（T03）

- 决策：`image_embeddings` 表保存向量本体，以“图片内容哈希 + 模型名称 + 模型版本”为唯一键，不关联具体文档。
- 理由：向量索引丢失时可以直接从数据库重建，不必重新运行 CLIP；内容相同的图片即使被多次上传，也只编码一次。
  唯一键中包含模型版本，更换模型后新旧向量可以并存，不会混用。
- 代价与局限：删除文档时不会删除对应的向量，因为其他文档可能共用它。不再被任何图片引用的向量需要由一致性检查（T18）清理。

### D11 子表对文档的外键使用级联删除（T03）

- 决策：片段、任务、图片、OCR 结果、共享、标签关联等表对 `documents` 的外键都是级联删除；`documents` 对 `users` 的外键不级联。
- 理由：硬删除文档记录是清理任务的最后一步，级联保证不留下孤儿数据。用户不级联是为了防止删除用户时连带删掉其全部文档。
- 代价与局限：日常删除是软删除，不触发级联；级联只在清理任务硬删除时发生。

### D12 普通用户可自行注册，管理员由命令行创建（T04，接口设计）

- 决策：注册接口只能创建普通用户；管理员账号通过服务器上的命令行工具创建，没有通过接口提升权限的途径。
- 理由：避免“第一个注册的用户自动成为管理员”这类隐含规则，也不需要设计用户管理界面。
- 状态：Barry 已于 2026-11-13 方案评审时确认，T06 实现。

### D13 共享按用户名指定，系统不提供用户列表接口（T04，接口设计）

- 决策：共享文档时由 owner 输入对方的用户名；没有列出或搜索全部用户的接口。
- 理由：共享只需要知道对方是谁，不需要暴露系统中有哪些用户。
- 状态：Barry 已于 2026-11-13 方案评审时确认，T08 实现。

### D14 密码用 Argon2id 哈希，登录令牌用 HS256 签名的 JWT（T06）

- 决策：密码用 argon2-cffi 库的 Argon2id 哈希后保存，参数取该库默认值；登录令牌是 PyJWT 签发的 JWT，签名算法固定为 HS256，密钥来自环境变量 `JWT_SECRET`（至少 32 个字符），有效期来自 `ACCESS_TOKEN_EXPIRE_SECONDS`（默认 3600 秒）。
- 理由：Argon2id 是成熟的密码哈希方案，每个密码单独加盐，哈希串里自带参数，以后调整参数不影响已有账号。单机系统里签发和校验令牌的是同一个进程，对称签名够用，不需要管理公私钥。
- 令牌里只放用户 ID 和过期时间，不放角色。每个请求都按用户 ID 查一次数据库，所以账号被删除或角色变化后立即生效。
- 代价与局限：每个请求多一次按主键的数据库查询。没有登出接口，也不能单独吊销某一个令牌；需要让全部令牌失效时更换 `JWT_SECRET`。

### D15 权限判断每次都查数据库，规则只写在一处（T06）

- 决策：`accessible_filter(user)` 生成“未删除且该用户可访问”的查询条件，`accessible_document_ids`、文档列表（T08）和检索的二次校验（T15）都使用它；`can_access` 判断单个文档。结果不缓存。
- 理由：附录 A10 要求删除和取消共享立即生效，缓存会破坏这一点；规则只有一处，不会出现列表和检索的权限判断不一致。
- 代价与局限：管理员的可访问集合等于全部未删除文档，文档很多时这个集合会比较大。毕设规模下可以接受。

### D16 任务框架的实现细节（T07）

附录 A2、A3 定了方向，这里记录落地时的具体做法。代码在 `shared/tasks.py` 和 `backend/app/worker/`。

- 尝试次数在领取时加一，不是在失败时。Worker 崩溃来不及回写也算一次尝试，所以一个必然让 Worker 崩溃的文件最多被尝试 `max_attempts` 次。
- 续租、标记成功、标记失败都带条件“任务仍由本 Worker 领取且状态为 `processing`”。Worker 卡住、租约被回收、任务被别人领走之后，它迟到的回写会被拒绝，不会覆盖别人的结果。
- 没有单独的回收进程。每次领取任务之前先回收过期租约。所有 Worker 都停止时没有人回收，但那时也没有人处理任务，结果不受影响。
- 失败后立即回到等待队列，不做退避等待。代价：临时性故障（例如 OpenSearch 短暂不可用）可能很快用完全部尝试次数；届时需要人工重试（`POST /api/tasks/{id}/retry`，T08）。
- 处理函数可以把失败标记为不可重试（例如压缩包超过解压上限），任务直接进入 `failed`。
- 每个任务在一个用 spawn 方式启动的子进程里执行。父进程负责计时和续租；超时就杀掉子进程；续租失败（租约已丢失或数据库出错）也杀掉子进程，并且不回写结果。
- Worker 处理满 `WORKER_MAX_TASKS` 个任务后退出，由外层循环重新拉起。
- 时间一律用数据库的 `now()`，不依赖各 Worker 进程的时钟。

局限：

- 子进程的内存上限用 `RLIMIT_AS` 实现，只在 Linux 上有效；macOS 的内核基本不执行这个限制。开发机是 macOS，所以本机上单个任务只受超时保护，内存上限未经验证。
- 测试状态：子进程执行和主循环的 22 项测试已在本机运行通过。领取、并发、崩溃恢复、幂等、重试上限这 18 项测试需要真实 PostgreSQL，本机没有，**未测试（Not Tested）**，只做了代码复核。论文中引用这些性质之前必须先在有 PostgreSQL 的环境里实际运行。

### D17 上传的步骤顺序与失败处理（T08）

- 决策：上传按“写临时文件并校验 → 数据库写入但不提交 → 文件移动到正式路径 → 数据库提交”执行。任何一步失败，数据库回滚，临时文件和已移动的文件都删除。
- 理由：Worker 只能看到已提交的任务，所以它看到解析任务时，文件一定已经在正式路径上。如果反过来先提交数据库再移动文件，Worker 可能领到一个文件还不存在的任务。
- 代价与局限：进程恰好在“文件已移动、数据库未提交”之间被杀掉时，会留下一个没有数据库记录的文件。它不影响任何功能，由一致性检查（T18）发现和清理。
- GLOBAL §6.2 写的顺序是“落盘到临时位置并校验 → 写数据库记录 → 移动到正式路径”。这里的实现与之一致，只是把“写数据库记录”拆成了写入和提交两步，提交放在移动之后。

### D18 上传大小在两处检查（T08）

- 决策：进入路由之前先看请求头 `Content-Length`，超过“上限 + 1 MB 表单余量”直接返回 413，不读请求体；存储层复制文件时再按精确的上限检查一次。
- 理由：FastAPI 在进入路由函数之前就会收完整个 multipart 请求体。只有存储层那一道检查的话，一个远超上限的文件要全部收完才被拒绝。
- 代价与局限：不带 `Content-Length` 的分块上传不会被第一道检查拦住，它会被收到系统临时目录后由第二道检查拒绝，不会进入正式存储。

- 理由：上传接口使用 `multipart/form-data`（api.md §5.2），FastAPI 解析它必须有这个包。

### D20 PDF 按页判断是否走 OCR 的规则（T09）

GLOBAL §2 P1 规定“某页文本层有效字符数低于配置阈值时，该页走 OCR”。落地时细化为三种情况。有效字符数不计空白字符，记为 n；阈值为配置项 `PDF_OCR_MIN_CHARS`，默认 20。

| 情况 | 处理 |
|---|---|
| n ≥ 阈值 | 采用文本层，该页产出一个 `source_type=body` 的文本块 |
| n < 阈值，页面上有图片或矢量图形 | 该页交给 OCR，不采用文本层 |
| n < 阈值，页面上没有图片和图形 | n > 0 时采用文本层；n = 0 是空白页，跳过 |

- 理由：第二种是扫描件，整页是一张图，文本层为空或只有页码之类的零星字符。第三种是只有一行标题的短页，页面上除了这点文字什么都没有，OCR 不会读到更多，直接用文本层；如果照字面只按字数判断，这类页会被送去 OCR，空白页也会被送去 OCR。
- 一页要么采用文本层，要么走 OCR，不会两者都有，所以同一页的文字不会以 `body` 和 `ocr` 两种来源重复出现。
- 默认值 20 是经验值，没有实验依据。它是实验参数，阶段五可以调整并观察对 B1、B2 的影响。
- 代价与局限：图文混排的页只要文本层达到阈值就不做 OCR，图片里的文字检索不到。文字被转成矢量轮廓的 PDF 没有文本层但有图形，会走 OCR。
- 某一页结构损坏时，整个文件按解析失败处理并写明页码，不跳过坏页继续——否则用户会以为全文都已经可以检索。
- 加密 PDF：需要打开口令的拒绝解析；只设了权限口令（限制打印、复制）的可以正常读取，照常解析。

### D21 PyMuPDF 锁定在 1.28.2（T09）

- 决策：`pymupdf==1.28.2`，不使用 2.x。
- 理由：2.0 起，PyMuPDF 把 onnxruntime、numpy、networkx、pymupdf-layout、pymupdf4llm 等列为必装依赖（2026-11-13 查 PyPI 元数据），主包也从约 24 MB 增加到约 67 MB。这些组件用于版面分析和面向大模型的导出，本项目用不到，也不符合 GLOBAL §5.6“不为展示技术增加无关组件”。1.28.2 是目前 1.x 的最新版本（2026-08 发布），没有任何附加依赖。
- 状态：Barry 于 2026-11-13 批准安装。
- 代价与局限：之后的新功能可能只出现在 2.x。PyMuPDF 采用 AGPL-3.0 与商业许可双重授权，作为毕业设计使用没有问题；如果将来系统要以闭源方式对外提供服务，需要重新评估许可。

### D22 前端的几项取舍（T10）

- 不引入状态管理库和 HTTP 库。登录状态用 Vue 自带的 `reactive` 保存在一个模块里（`src/auth.ts`），请求用浏览器自带的 `fetch` 封装（`src/api/client.ts`）。理由：目前只有“当前用户”这一份全局状态，接口调用也很规整，多装两个库没有收益。
- 登录令牌保存在浏览器的 `localStorage`。理由：刷新页面后不必重新登录。代价：页面一旦被注入恶意脚本，令牌可能被读走。本项目不渲染用户提供的 HTML，令牌有效期默认 1 小时。
- 开发时由 Vite 把 `/api` 和 `/health` 转发到后端（`vite.config.ts`），浏览器看到的始终是同一个来源，后端不需要配置跨域。代价：生产部署时需要一个反向代理做同样的转发，T30 的部署说明里要写。
- 下载先用带令牌的请求取回文件内容，再由浏览器保存。理由：下载接口需要登录，普通链接带不上令牌。代价：文件会先完整读入浏览器内存，大文件（接近 50 MB 上限）会占用相应内存。
- 列表里只要有“等待处理”或“处理中”的文档，就每 5 秒自动刷新一次，直到全部处理完。
- 前端的登录判断和按钮显隐只决定“显示什么”，不是权限控制。权限由后端每个接口校验（GLOBAL §7.2）。
- Element Plus 整体引入，没有做按需加载。代价：打包后的主文件约 870 KB（gzip 后约 280 KB）。毕设规模下可以接受。
- TypeScript 锁定在 6.0.3。理由：7.x 是用另一种语言重写的版本，vue-tsc 3.3.14 还不支持，装上后类型检查无法启动。
