## 1. 附录 A 的已定决策

### 1.1 数据库与任务

**A1 关系数据库使用 PostgreSQL**

- 决策：PostgreSQL 是系统唯一的关系数据库。
- 理由：它支持 `SELECT … FOR UPDATE SKIP LOCKED`，多个 Worker 可以并发领取任务而不互相阻塞，
  因此同一个数据库可以同时承担业务数据存储和任务队列两个职责。
- 代价与局限：部署时需要单独运行数据库服务，比嵌入式数据库多一个组件。

**A2 任务队列使用 PostgreSQL 任务表，不引入 Redis、Celery 等中间件**

- 决策：后台任务记录在 `processing_tasks` 表中，Worker 直接从这张表领取。
- 理由：任务状态、重试次数、失败原因与业务数据在同一个数据库、同一个事务里，
  “写入文档记录”和“创建解析任务”可以一起提交或一起回滚，不存在两个系统之间不一致的问题；系统的组件数量也最少。
- 代价与局限：Worker 靠轮询发现新任务，有秒级延迟；吞吐量受数据库限制。对单机毕业设计的规模，这两点都可以接受。

**A3 Worker 采用租约、超时回收、子进程隔离和定期重启**

- 决策：领取任务时写入租约到期时间，处理中定期续约；租约过期仍处于处理中的任务被回收。
  每个文件在子进程中处理，设超时和内存上限。Worker 处理一定数量的任务后自动退出重启。
- 理由：文档解析和 OCR 面对的是任意用户文件，可能卡死、崩溃或耗尽内存。
  租约保证 Worker 崩溃后任务不会永远停在“处理中”；子进程保证一个坏文件不会拖垮整个 Worker；
  定期重启避免长时间运行后的内存增长。
- 代价与局限：每个任务多一次启动子进程的开销；租约时长需要权衡——太短会误回收仍在正常处理的任务，太长则崩溃后恢复慢。

### 1.2 AI 组件的隔离

**A4 PaddleOCR 与 Chinese-CLIP 各用独立的虚拟环境和独立进程**

- 决策：系统使用三套 Python 虚拟环境：主环境、OCR 环境、CLIP 环境。OCR 和 CLIP 各自作为独立进程运行。
- 理由：PaddleOCR 依赖 PaddlePaddle，Chinese-CLIP 依赖 PyTorch，两套深度学习框架装在同一环境中容易产生依赖冲突。
  进程隔离还带来一个好处：任何一个 AI 组件崩溃都不影响 API 服务。
- 代价与局限：要维护三份依赖清单；进程之间只能通过数据库任务表或 HTTP 协作，不能直接调用函数。

**A5 查询文本的编码由常驻模型服务完成，调用带超时，失败即降级**

- 决策：CLIP 模型只在模型服务进程启动时加载一次。检索时 API 通过 HTTP 请求模型服务编码查询文本，
  并设置超时；超时、失败或健康检查不通过时，本次查询只使用文本通道，并在响应中标记图像通道不可用。
- 理由：模型加载耗时长，不能放在检索请求里；AI 组件故障不应影响核心的文本检索。
- 代价与局限：每次带图像通道的检索多一次本机 HTTP 调用；降级时结果不含图像通道的贡献，用户需要从响应标记中得知这一点。

### 1.3 统一单位与 ID

**A6 融合、评测、权限的统一单位是 document_id（文件级）**

- 决策：所有检索通道的结果最终都聚合到文件；RRF 融合、相关性标注、权限判断都以文件为单位。
  片段和图片只作为命中证据展示。
- 理由：文本通道返回的是片段，图像通道返回的是图片，粒度不同的结果无法直接融合；
  统一到文件之后，融合、评测和权限使用同一个单位，标注粒度也随之确定。
- 代价与局限：评测不衡量“定位到的片段是否准确”，这一点需要用来源定位准确率单独评估；
  一个很长的文件只要有一个片段相关就算命中。

**A7 确定性 ID：chunk_id = {document_id}:{parse_version}:{seq}**

- 决策：片段 ID 由文档 ID、解析版本和序号拼成，不使用随机 ID。
- 理由：同一文档用同一解析版本重新处理时，生成的 ID 完全相同，写入数据库和索引时是覆盖而不是新增，
  任务重复执行因此天然幂等。解析参数变化时 `parse_version` 随之变化，旧版本的片段可以按版本整体删除。
- 代价与局限：`parse_version` 中不能出现冒号（见 D3）。

**A15 不做文档版本管理；替换文件即新建文档**

- 决策：系统不保留文件的历史版本。要替换文件，就上传一个新文档并删除旧文档。
- 理由：一个文档永远对应一份文件内容，ID 规则和一致性设计都更简单。
- 代价与局限：替换后 `document_id` 改变，原有的共享关系和标签不会自动继承。

### 1.4 检索与索引

**A8 双索引：doc_meta（文件级）与 chunks（片段级，含 source_type）**

- 决策：文件名和标签写入文件级的 `doc_meta` 索引；正文和 OCR 文字的片段写入 `chunks` 索引，
  每个片段带 `source_type` 字段，取值为 `body`（文档自带文本）或 `ocr`（OCR 识别文字）。
- 理由：如果把文件名冗余写进每个片段，一个文件有多少片段，文件名就被重复计分多少次，片段多的长文件会被不合理地抬高。
  分成两个索引后，对照实验 B0 只查 `doc_meta`，B1 与 B2 只差一个 `source_type` 过滤条件，不需要维护多套索引。
- 代价与局限：一次检索要查两个索引，结果需要在应用层合并。

**A12 向量检索采用精确检索，权限范围作为前置过滤条件**

- 决策：图片向量检索逐一计算查询向量与候选向量的相似度，不使用 HNSW 等近似索引；
  用户可访问的文档集合作为检索前的过滤条件。
- 理由：毕业设计规模下图片数量有限，精确计算的延迟可以接受，并且省去近似索引的参数调优，实验结果也不受近似误差影响。
  权限前置过滤避免了“先取前 k 条再过滤”造成的结果数量不足。
- 代价与局限：检索延迟随图片数量线性增长。数据规模增长到延迟不可接受时需要重新评估，届时须经 Barry 确认。

**A13 中文分词方案在环境验证阶段实测确定**

- 决策：分词器不预先指定，在本机实测后确定，配置纳入版本管理。候选是官方的 analysis-smartcn 插件和社区的 IK 插件。
- 理由：OpenSearch 默认分词器把中文逐字切开，检索效果差；IK 插件必须与 OpenSearch 版本严格匹配，能否安装要实测才知道。
- 状态：**Barry 于 2026-11-14 选定 analysis-smartcn，未经本机实测，阶段五可换。** 选定时 OpenSearch 和两个插件都没有在任何机器上运行过（本机没有 Docker 和 Java），依据是 smartcn 为官方插件、与 OpenSearch 同版本发布、安装风险低；IK 与 2.19.1 是否有匹配版本未核实。实现方式见 D26，补测步骤见 `docs/untested.md` 第 6 节。

**A14 OpenSearch 降级预案：Python 端 BM25 + faiss，仅记录不实现**

- 决策：如果环境实测证明本机资源无法稳定运行 OpenSearch，备选方案是在 Python 端实现 BM25 并用 faiss 做向量检索，
  替换范围限定在检索层（M8、M10）内部。该预案只作为文档记录，不与 OpenSearch 同时实现。
- 理由：给硬件资源不足的情况留一条退路，同时避免同时维护两套检索实现。
- 状态：是否启用**待定**，见第 2 节。启用前须经 Barry 确认。

### 1.5 来源定位、删除与权限

**A9 来源定位为多态字段；Word 只定位到段落**

- 决策：来源定位按文件格式有四种形态：PDF 定位到页，Word 定位到段落序号，Excel 定位到工作表和单元格范围，图片定位到图片 ID。
- 理由：不同格式能可靠获得的位置信息不同。python-docx 读不到页码——Word 的分页是排版时才计算出来的——所以 Word 不提供页码，也不伪造。
- 代价与局限：Word 文档的检索结果不能跳转到具体页。论文中必须表述为“段落级定位”。

**A10 软删除，检索返回前用数据库二次校验**

- 决策：删除文件时先在数据库中写入删除时间，文件立即对所有查询不可见；索引和磁盘文件由后台清理任务删除。
  检索在返回结果前，用数据库校验每个候选文件，只保留未删除且当前用户有权访问的。
- 理由：搜索索引的更新是异步的，单靠索引无法保证“删除后立即搜不到”和“取消共享后立即搜不到”。
  数据库校验是这两点的唯一保证机制，因此不得以性能为由去掉。
- 代价与局限：每次检索多一次数据库查询；被过滤掉的候选会让实际返回的结果数少于请求的数量。

**A11 权限模型：owner 私有、管理员、可选的指定用户共享**

- 决策：普通用户只能访问自己上传的文档；管理员可以访问全部；owner 可以把文档共享给指定用户，被共享者获得只读和检索权限。
- 理由：满足多用户文档管理的基本需求，同时不进入部门、组织、多级权限等企业级功能。
- 代价与局限：不能按组共享，文档多时逐个共享比较繁琐。

### 1.6 范围控制

**A16 预览：PDF 用 pdf.js，图片原生显示，Word 和 Excel 展示抽取出的文本**

- 决策：只有 PDF 和图片提供原样预览；Word 和 Excel 显示系统抽取出的文本，并提供原文件下载。
- 理由：Word、Excel 的原样排版预览实质上是在线 Office，工作量大且与检索这一论文主线无关。
- 代价与局限：Word、Excel 的预览看不到原始格式、图表和公式。

**A17 图片与文档只做结构关联；文档内嵌图片的抽取归入 P4**

- 决策：系统只记录“图片属于哪个文档”。独立上传的图片本身就是一个文档；抽取 Word、PDF 内嵌的图片属于非核心增强，暂不实现。
- 理由：控制范围。自动判断“哪张图片与哪段文字语义相关”是另一个研究问题。
- 代价与局限：文档内部的插图目前不能被图像通道检索到。扫描版 PDF 的整页会做 OCR，但不做图像向量。

### 1.7 实验与开发过程

**A18 评测查询按文字型、视觉型、混合型分层；标注从阶段二起并行**

- 决策：查询集分为三类，实验结果按类别分层报告。相关性标注从阶段二开始每周进行。
- 理由：文字型查询天然有利于 BM25，视觉型查询天然有利于 CLIP；只报告总体平均值，
  结论会被查询集中各类型的比例左右。分层报告才能说明每个通道在什么情况下有贡献。
- 代价与局限：标注工作量更大；各层的查询数量较少时，指标的波动会比较大，需要如实说明。

**A19 开发按 MVP-0、MVP-1、MVP-2 分层，从数据契约和上传入库链路起步**

- 决策：先定义数据契约，再实现存储、文档管理和任务框架，然后逐层增加格式和检索通道。每一层都要求端到端可演示、有测试。
- 理由：ID 规则和任务机制是后续所有模块的基础，先定下来可以避免返工；
  分层交付保证即使时间不足，也有一个完整可用的系统，而不是多个半成品模块。

## 3. 实现过程中的决策

### D1 配置只从环境变量读取，启动时一次性校验（T01）

- 决策：后端的全部配置来自环境变量或项目根目录的 `.env` 文件。启动时检查必填项，缺失或不合法就退出，并列出出问题的变量名。
- 理由：数据库地址、密码不能散落在代码中，也不能提交到 Git；启动时就报错，比运行到一半才发现配置缺失更容易排查。
- 代价与局限：错误信息只给出变量名，不显示变量的值，因为连接串中可能带密码。

### D2 健康检查如实报告依赖状态，而不是报错（T01）

- 决策：`GET /health` 分别检查数据库、OpenSearch 和 CLIP 服务，任何一项不可用时接口仍返回 200，在响应体中标明哪一项不可用。
- 理由：CLIP 服务不可用是系统允许的正常降级状态，不应让健康检查失败；三项分开报告才能看出是哪个组件出了问题。

### D3 parse_version 只允许字母、数字、点、下划线和连字符（T02）

- 决策：`parse_version` 的字符集受限，不能包含冒号。
- 理由：`chunk_id` 用冒号分隔三段（A7），`parse_version` 中出现冒号会使 ID 无法可靠地拆回各部分。

### D4 ParsedDocument 不包含 document_id（T02）

- 决策：解析结果中没有文档 ID，文档 ID 在切分阶段由调用方传入。
- 理由：解析器是“文件路径 → 解析结果”的纯函数，不需要知道文件在系统中的身份，因此可以脱离数据库和 Web 系统单独测试。

### D5 契约对象不可修改，且禁止多余字段（T02）

- 决策：所有数据契约对象创建后不能修改字段；传入契约中没有定义的字段会报错。
- 理由：契约对象在模块之间传递，不可修改可以排除“某个模块悄悄改了数据”这类问题；
  禁止多余字段可以让字段名的拼写错误立即暴露，而不是被忽略。

### D6 ID 只接受一种写法（T02）

- 决策：解析 `chunk_id`、`image_id` 时，UUID 必须是标准小写形式，数字不能带前导零或正负号。
- 理由：数据库主键和索引文档 ID 都是按字符串比较的。如果同一个对象可以有多种写法，覆盖写入就会变成新增，幂等性失效。

### D7 枚举用字符串加 CHECK 约束，不用数据库的 ENUM 类型（T03）

- 决策：状态、角色、`source_type` 等字段在数据库中是字符串列，用 CHECK 约束限定取值。
- 理由：PostgreSQL 的 ENUM 类型增减取值需要专门的迁移操作，且不易回退；CHECK 约束只需修改约束本身。
- 代价与局限：取值在模型代码和迁移脚本中各出现一次，修改时两处都要改（有测试比对模型与迁移是否一致）。

### D8 文档处理状态与任务状态使用相同的四个取值（T03）

- 决策：`documents.status` 取 `pending`、`processing`、`succeeded`、`failed`，与任务状态一致。
- 理由：用户在文件列表中看到的状态与后台任务的状态对应，不需要另一套状态映射。
- 代价与局限：一个文档可能有多个任务（解析、OCR、向量）。T14 定下的规则是文档状态只跟随 parse 任务，见 D27。OCR、向量任务的成败不反映在文档状态里，用户要在任务列表里查看。

### D9 片段正文保存在数据库中（T03）

- 决策：`document_chunks` 表保存每个片段的完整文本，而不是只保存在搜索索引里。
- 理由：Word、Excel 的预览要显示抽取出的文本；索引丢失或需要更换分词器时，可以直接从数据库重建，不必重新解析和 OCR（重建入口见 D31）。
- 代价与局限：文本在数据库和索引中各存一份，占用更多磁盘。

### D10 图片向量保存在数据库中，按内容哈希去重（T03）

- 决策：`image_embeddings` 表保存向量本体，以“图片内容哈希 + 模型名称 + 模型版本”为唯一键，不关联具体文档。
- 理由：向量索引丢失时可以直接从数据库重建，不必重新运行 CLIP；内容相同的图片即使被多次上传，也只编码一次。
  唯一键中包含模型版本，更换模型后新旧向量可以并存，不会混用。
- 代价与局限：删除文档时不会删除对应的向量，因为其他文档可能共用它。不再被任何图片引用的向量需要由一致性检查清理；T18 的检查（D31）还没有覆盖向量，留到 T21 有数据后补上（T21 已补上，见 D35）。

### D11 子表对文档的外键使用级联删除（T03）

- 决策：片段、任务、图片、OCR 结果、共享、标签关联等表对 `documents` 的外键都是级联删除；`documents` 对 `users` 的外键不级联。
- 理由：硬删除文档记录是清理任务的最后一步，级联保证不留下孤儿数据。用户不级联是为了防止删除用户时连带删掉其全部文档。
- 代价与局限：日常删除是软删除，不触发级联；级联只在清理任务硬删除时发生。

### D12 普通用户可自行注册，管理员由命令行创建（T04，接口设计）

- 决策：注册接口只能创建普通用户；管理员账号通过服务器上的命令行工具创建，没有通过接口提升权限的途径。
- 理由：避免“第一个注册的用户自动成为管理员”这类隐含规则，也不需要设计用户管理界面。
- 状态：Barry 已于 2026-11-13 方案评审时确认，T06 实现。

### D13 共享按用户名指定，系统不提供用户列表接口（T04，接口设计）

- 决策：共享文档时由 owner 输入对方的用户名；没有列出或搜索全部用户的接口。
- 理由：共享只需要知道对方是谁，不需要暴露系统中有哪些用户。
- 状态：Barry 已于 2026-11-13 方案评审时确认，T08 实现。

### D14 密码用 Argon2id 哈希，登录令牌用 HS256 签名的 JWT（T06）

- 决策：密码用 argon2-cffi 库的 Argon2id 哈希后保存，参数取该库默认值；登录令牌是 PyJWT 签发的 JWT，签名算法固定为 HS256，密钥来自环境变量 `JWT_SECRET`（至少 32 个字符），有效期来自 `ACCESS_TOKEN_EXPIRE_SECONDS`（默认 3600 秒）。
- 理由：Argon2id 是成熟的密码哈希方案，每个密码单独加盐，哈希串里自带参数，以后调整参数不影响已有账号。单机系统里签发和校验令牌的是同一个进程，对称签名够用，不需要管理公私钥。
- 令牌里只放用户 ID 和过期时间，不放角色。每个请求都按用户 ID 查一次数据库，所以账号被删除或角色变化后立即生效。
- 代价与局限：每个请求多一次按主键的数据库查询。没有登出接口，也不能单独吊销某一个令牌；需要让全部令牌失效时更换 `JWT_SECRET`。

### D15 权限判断每次都查数据库，规则只写在一处（T06）

- 决策：`accessible_filter(user)` 生成“未删除且该用户可访问”的查询条件，`accessible_document_ids`、文档列表（T08）和检索的二次校验（T15）都使用它；`can_access` 判断单个文档。结果不缓存。
- 理由：附录 A10 要求删除和取消共享立即生效，缓存会破坏这一点；规则只有一处，不会出现列表和检索的权限判断不一致。
- 代价与局限：管理员的可访问集合等于全部未删除文档，文档很多时这个集合会比较大。毕设规模下可以接受。

### D16 任务框架的实现细节（T07）

附录 A2、A3 定了方向，这里记录落地时的具体做法。代码在 `shared/tasks.py` 和 `backend/app/worker/`。

- 尝试次数在领取时加一，不是在失败时。Worker 崩溃来不及回写也算一次尝试，所以一个必然让 Worker 崩溃的文件最多被尝试 `max_attempts` 次。
- 续租、标记成功、标记失败都带条件“任务仍由本 Worker 领取且状态为 `processing`”。Worker 卡住、租约被回收、任务被别人领走之后，它迟到的回写会被拒绝，不会覆盖别人的结果。
- 没有单独的回收进程。每次领取任务之前先回收过期租约。所有 Worker 都停止时没有人回收，但那时也没有人处理任务，结果不受影响。
- 失败后立即回到等待队列，不做退避等待。代价：临时性故障（例如 OpenSearch 短暂不可用）可能很快用完全部尝试次数；届时需要人工重试（`POST /api/tasks/{id}/retry`，T08）。
- 处理函数可以把失败标记为不可重试（例如压缩包超过解压上限），任务直接进入 `failed`。约定：处理函数抛出的异常带有 `retryable = False` 属性（`parsing.ParseError` 默认如此）时，这个标记会从子进程传回 Worker，再传给队列。2026-11-14 核查前这个标记在子进程边界上丢失，所有失败都按可重试处理；已修复并加了测试。
- 每个任务在一个用 spawn 方式启动的子进程里执行。父进程负责计时和续租；超时就杀掉子进程；续租失败（租约已丢失或数据库出错）也杀掉子进程，并且不回写结果。
- Worker 处理满 `WORKER_MAX_TASKS` 个任务后退出，由外层循环重新拉起。
- 时间一律用数据库的 `now()`，不依赖各 Worker 进程的时钟。

局限：

- 子进程的内存上限用 `RLIMIT_AS` 实现，只在 Linux 上有效；macOS 的内核基本不执行这个限制。开发机是 macOS，所以本机上单个任务只受超时保护，内存上限未经验证。
- 测试状态：子进程执行和主循环的 22 项测试已在本机运行通过。领取、并发、崩溃恢复、幂等、重试上限这 18 项测试需要真实 PostgreSQL，本机没有，**未测试（Not Tested）**，只做了代码复核。论文中引用这些性质之前必须先在有 PostgreSQL 的环境里实际运行。

### D17 上传的步骤顺序与失败处理（T08）

- 决策：上传按“写临时文件并校验 → 数据库写入但不提交 → 文件移动到正式路径 → 数据库提交”执行。任何一步失败，数据库回滚，临时文件和已移动的文件都删除。
- 理由：Worker 只能看到已提交的任务，所以它看到解析任务时，文件一定已经在正式路径上。如果反过来先提交数据库再移动文件，Worker 可能领到一个文件还不存在的任务。
- 代价与局限：进程恰好在“文件已移动、数据库未提交”之间被杀掉时，会留下一个没有数据库记录的文件。它不影响任何功能，由一致性检查发现和清理（D31 的 `orphan_file`，修复类别 `orphan-files`）。
- GLOBAL §6.2 写的顺序是“落盘到临时位置并校验 → 写数据库记录 → 移动到正式路径”。这里的实现与之一致，只是把“写数据库记录”拆成了写入和提交两步，提交放在移动之后。

### D18 上传大小在两处检查（T08）

- 决策：进入路由之前先看请求头 `Content-Length`，超过“上限 + 1 MB 表单余量”就返回 413，请求体读取后直接丢弃，不落盘、不进内存；存储层复制文件时再按精确的上限检查一次。
- 2026-11-14 修订：最初的实现不读请求体就应答并断开连接。核查时用真实后端加开发代理实测，发现客户端此时还在发送数据，连接被重置，用户看到的是 502 而不是 413。现在改为把请求体读完丢弃后再应答；读取量超过 256 MB 时才直接断开。
- 理由：FastAPI 在进入路由函数之前就会收完整个 multipart 请求体。只有存储层那一道检查的话，一个远超上限的文件要全部收完才被拒绝。
- 代价与局限：不带 `Content-Length` 的分块上传不会被第一道检查拦住，它会被收到系统临时目录后由第二道检查拒绝，不会进入正式存储。

### D20 PDF 按页判断是否走 OCR 的规则（T09）

GLOBAL §2 P1 规定“某页文本层有效字符数低于配置阈值时，该页走 OCR”。落地时细化为三种情况。有效字符数不计空白字符，记为 n；阈值为配置项 `PDF_OCR_MIN_CHARS`，默认 20。

| 情况 | 处理 |
|---|---|
| n ≥ 阈值 | 采用文本层，该页产出一个 `source_type=body` 的文本块 |
| n < 阈值，页面上有图片或矢量图形 | 该页交给 OCR，不采用文本层 |
| n < 阈值，页面上没有图片和图形 | n > 0 时采用文本层；n = 0 是空白页，跳过 |

- 理由：第二种是扫描件，整页是一张图，文本层为空或只有页码之类的零星字符。第三种是只有一行标题的短页，页面上除了这点文字什么都没有，OCR 不会读到更多，直接用文本层；如果照字面只按字数判断，这类页会被送去 OCR，空白页也会被送去 OCR。
- 一页要么采用文本层，要么走 OCR，不会两者都有，所以同一页的文字不会以 `body` 和 `ocr` 两种来源重复出现。
- 默认值 20 是经验值，没有实验依据。它是实验参数，阶段五可以调整并观察对 B1、B2 的影响。
- 代价与局限：图文混排的页只要文本层达到阈值就不做 OCR，图片里的文字检索不到。文字被转成矢量轮廓的 PDF 没有文本层但有图形，会走 OCR。
- 某一页结构损坏时，整个文件按解析失败处理并写明页码，不跳过坏页继续——否则用户会以为全文都已经可以检索。
- 加密 PDF：需要打开口令的拒绝解析；只设了权限口令（限制打印、复制）的可以正常读取，照常解析。

- 状态：Barry 于 2026-11-13 批准安装。

### D22 前端的几项取舍（T10）

- 不引入状态管理库和 HTTP 库。登录状态用 Vue 自带的 `reactive` 保存在一个模块里（`src/auth.ts`），请求用浏览器自带的 `fetch` 封装（`src/api/client.ts`）。理由：目前只有“当前用户”这一份全局状态，接口调用也很规整，多装两个库没有收益。
- 登录令牌保存在浏览器的 `localStorage`。理由：刷新页面后不必重新登录。代价：页面一旦被注入恶意脚本，令牌可能被读走。令牌有效期默认 1 小时。前端只在两处用 `v-html`，都是先把文字整体转义、再只插入 `<em>`：检索摘要经 `utils/snippet.ts` 的 `sanitizeSnippet` 白名单清洗（后端已转义，前端再清洗一次）；预览页的关键词高亮经 `highlightText` 先转义再标记。其余地方仍不渲染 HTML（T16 修订，见 D29）。
- 开发时由 Vite 把 `/api` 和 `/health` 转发到后端（`vite.config.ts`），浏览器看到的始终是同一个来源，后端不需要配置跨域。代价：生产部署时需要一个反向代理做同样的转发，T30 的部署说明里要写。
- 下载先用带令牌的请求取回文件内容，再由浏览器保存。理由：下载接口需要登录，普通链接带不上令牌。代价：文件会先完整读入浏览器内存，大文件（接近 50 MB 上限）会占用相应内存。
- 列表里只要有“等待处理”或“处理中”的文档，就每 5 秒自动刷新一次，直到全部处理完。
- 前端的登录判断和按钮显隐只决定“显示什么”，不是权限控制。权限由后端每个接口校验（GLOBAL §7.2）。
- Element Plus 整体引入，没有做按需加载。代价：打包后的主文件约 870 KB（gzip 后约 280 KB）。毕设规模下可以接受。
- TypeScript 锁定在 6.0.3。理由：7.x 是用另一种语言重写的版本，vue-tsc 3.3.14 还不支持，装上后类型检查无法启动。

### D24 Word、Excel、图片解析器的规则（T11）

**新增依赖。** main 环境增加 `python-docx==1.2.0`（带入 lxml 6.1.3）和 `openpyxl==3.1.5`（带入 et-xmlfile 2.0.0），都是 GLOBAL §3.1 指定的解析库，装的是 2026-11-14 时 PyPI 上的最新版本。Barry 于 2026-11-14 批准。图片的尺寸读取和解码检查用已有的 PyMuPDF，没有引入 Pillow。

**Word。**

- 每个非空段落产出一个文本块，定位为 `{type: "docx_para", para_index}`，不提供页码（附录 A9）。
- `para_index` 从 0 开始，按文档顺序给正文里的每个段落编号；表格单元格里的段落也算在内（逐行、逐格、格内从上到下，嵌套表格同样展开）。空段落占一个编号但不产出文本块，这样编号只取决于文档结构。
- 横向合并的单元格只读一次（按 XML 里真实存在的单元格遍历，不用 python-docx 的 `row.cells`，后者会把合并单元格按跨的列数重复返回）。
- 代价与局限：不提取页眉、页脚、脚注、批注、文本框和内容控件（sdt）里的文字；表格被拆成一个个单元格段落，行列关系不保留；内嵌图片不抽取（P4，附录 A17），所以图片里的文字检索不到。

**Excel。**

- 每个有内容的行产出一个文本块：该行非空单元格从左到右用制表符连接；定位为 `{type: "xlsx_range", sheet, range}`，范围是该行第一个到最后一个非空单元格（如 `B3:F3`，只有一格时为 `B3`）。按行组合并成检索片段由 T12 的切分完成。
- 公式取 Excel 上次保存时缓存的计算结果，不取公式本身。数字、日期按值转成文本，不套用单元格的显示格式。合并单元格的内容只出现在左上角一格。隐藏的工作表照常提取；图表工作表不提取。
- 用 openpyxl 的只读模式逐行流式读取，并且不采用文件里声明的表格范围（它可以被伪造成整张表，让每行补出一万六千多个空单元格）。
- 代价与局限：不是由 Excel 保存的文件（程序生成后从未用 Excel 打开过），公式单元格没有缓存值，会被当成空单元格；显示为“50%”的单元格提取出来是“0.5”，按显示文本搜索搜不到；旧版 `.xls` 不支持。

**图片。**

- 图片不产出任何文本块，整张登记为一个 OCR 对象（`{type: "image", image_id}`）。独立图片的 `image_id` 就是 `document_id`，由调用方传入，解析器本身仍然不知道文档 ID。
- 另提供 `read_image_info` 读出像素宽高，供 T14 写入 `image_assets`。`ParsedDocument` 契约没有改动。
- 检查顺序：先从文件头读尺寸并检查像素数上限，再检查结束标记（PNG 的 IEND、JPEG 图像数据之后的 EOI），最后完整解码一次并核对尺寸。先查上限再解码，是因为几 KB 的图片可以声称有几十亿像素。结束标记要单独查，是因为实测 PyMuPDF 对截断的图片很宽容：只剩 40 字节文件头的 PNG 也能“解码成功”，缺的部分补成灰色。
- 代价与局限：尺寸是文件里存储的宽高，不考虑 EXIF 旋转标记；每张图片在解析阶段多解码一次；极少数没有结束标记但看图软件能打开的 JPEG 会被拒绝。

**zip 炸弹防护与超时。**

- docx / xlsx 交给解析库之前先读 zip 目录：条目数超过 `PARSE_ZIP_MAX_ENTRIES`（默认 5000）、声明的解压后总大小超过 `PARSE_ZIP_MAX_TOTAL_BYTES`（默认 200 MB）、或含有加密条目，都直接拒绝，任务标记为不可重试的失败。
- 只看声明的大小就够的理由：两个解析库都通过标准库 `zipfile` 读取，而 `zipfile` 读一个条目时最多只输出目录里声明的字节数，谎报大小的条目会在声明处截断并校验失败（有测试验证）。
- 图片的像素数上限为 `PARSE_IMAGE_MAX_PIXELS`（默认 1 亿，即 10000×10000）。
- 三个默认值都是经验值，没有实验依据。
- 解析超时没有在解析器内部另做：解析库的大部分时间花在 C 代码里，Python 线程内的超时打断不了它。超时由 Worker 在子进程边界执行（D16，`WORKER_TASK_TIMEOUT_SECONDS`，默认 600 秒，超时即杀掉子进程），T14 把解析器接进任务处理函数后即受它保护。
- 代价与局限：XML 实体膨胀（billion laughs）没有单独防护，依赖 lxml / libxml2 的默认限制和上面的超时兜底；解压后 200 MB 以内的 XML 载入内存后仍可能占用数倍空间，而内存上限在 macOS 上不生效（D16）。

### D25 切分规则与 parse_version（T12）

**比较过的方案。**

| 方案 | 做法 | 问题 |
|---|---|---|
| 每块单独成片段 | 解析器的每个文本块就是一个片段，过长才拆 | Word 表格逐格、Excel 逐行，会产生大量“张三”“95”这种几个字的片段：没有上下文，BM25 的长度归一又会让极短片段得分偏高，片段数量也成倍增加 |
| 全部按长度连续打包 | 不看来源，按字数把相邻块连成片段 | PDF 跨页合并后，片段只能带一个页码，第二页的文字会被定位到第一页，违背“真实可用的来源定位”（GLOBAL §15） |
| **按定位类型决定能否合并（采用）** | 见下 | Word 的定位只能指向片段起始段落（见代价与局限） |

**决策。**

- 能否合并由来源定位的类型决定：
  - PDF 页、图片：不与任何块合并，过长时才拆开。一页或一张图片的文字只出现在指向它自己的片段里。
  - Word 段落：相邻段落按整段打包，不超过 `CHUNK_MAX_CHARS`。定位是片段的起始段落。
  - Excel 行：同一工作表的相邻行按整行打包（DEVPLAN 的“按行组切分”），不跨工作表。定位是这些行的外接矩形，例如 `B2:C2`、`B5:D5` 合并后是 `B2:D5`。
- 重叠：打包时，下一个片段以上一个片段末尾的若干整块开头，总长不超过 `CHUNK_OVERLAP_CHARS`。整块重叠时，片段的定位仍然准确；末尾的块比重叠上限长时不带。单独一块就超过上限的（长段落、长页、长 OCR 文字）按字符窗口拆开，相邻两段重叠 `CHUNK_OVERLAP_CHARS` 个字符，每段都使用这一块的定位。
- 拆开时，在窗口的最后四分之一里找断点，优先级为：换行，句末标点（。！？；!?;），空白和逗号。找不到才在上限处硬断开。英文句点不单独作断点，因为“3.14”“v1.2”里的点不是句末。
- 长度按字符数计算，中文一个字、英文一个字母都算一个。默认 `CHUNK_MAX_CHARS=500`、`CHUNK_OVERLAP_CHARS=50`，配置要求重叠不超过上限的一半。两个默认值都是经验值，阶段五作为实验参数调整。
- parse_version 由会影响片段内容的全部输入确定性地算出：切分算法版本（代码常量 `CHUNKER_VERSION`，改切分规则时加一）、两个切分参数、解析器名称和版本、调用方传入的解析参数（例如 PDF 的 `pdf_ocr_min_chars`）。形如 `c1-m500-o50-1a2b3c4d5e6f`：前缀便于肉眼辨认参数，后面 12 位是全部输入的 SHA-256。任何一项变化，版本号都随之变化，旧版本的片段整体删除（附录 A7）。
- 切分模块只依赖 `shared` 和标准库，不依赖 backend 的其他部分。已在 T17 整体移到 `shared/chunking`，供 OCR Worker（ocr 环境）使用（D30）。
- 同一文档、同一 parse_version 下分几次切分时（正文一次，各页 OCR 各一次），`chunk_blocks` 用 `seq_start` 指定起始序号，由调用方保证各次的序号区间不重叠。具体怎么分配留给 T14/T17。

**代价与局限。**

- Word 片段只能定位到它的起始段落。命中的文字可能在片段后面几段，前端跳转时会落在片段开头。如果要精确到段落范围，需要给 `DocxParaLocator` 增加一个结束段落字段，这属于数据契约变更（T02），没有做。
- Excel 的外接矩形可能比实际有内容的单元格大，例如一行在 A–C 列、下一行在 A–Z 列。
- Excel 每个片段不重复表头：表头行之后的片段里只有数据，没有列名，按“列名 + 值”的方式搜索可能搜不到后面的行。是否给每个片段补上表头，需要实验确定，记在 DEVPLAN §4。
- 重叠的文字在两个片段里各出现一次，同一文件的 BM25 分数可能因此略有偏高；检索时按文件聚合并只取最高分片段（GLOBAL §4.2），影响有限。

### D26 文本索引的结构与写入方式（T13）

计划经 Barry 批准后实现；分词器按 A13 的选定用 analysis-smartcn。**下面的一切都没有在真实 OpenSearch 上运行过**（见 `docs/untested.md` 第 6 节）。

**访问方式。**

- 用 httpx 直接调用 OpenSearch 的 REST 接口，不引入 opensearch-py：M8 只用到建索引、批量写入、按条件删除几个接口，httpx 已是 main 环境的依赖。
- 统一的超时来自 `OPENSEARCH_TIMEOUT_SECONDS`（默认 10 秒）。索引名可以加前缀 `OPENSEARCH_INDEX_PREFIX`（默认为空），测试用它得到独立的索引，不碰正式数据。
- 本模块不重试，重试交给任务框架（A3）。

**索引结构**（`shared/text_index/mappings/`，纳入版本管理；T13 时在 `backend/app/modules/text_index/`，T17 移到 shared，见 D30）。

| 索引 | `_id` | 字段 |
|---|---|---|
| `doc_meta` | `document_id` | `document_id`（keyword）、`filename`（text，另有 `.raw` keyword 子字段）、`tags`（text，另有 `.raw` keyword 子字段） |
| `chunks` | `chunk_id` | 与 `Chunk` 契约完全一致：`chunk_id`、`document_id`、`parse_version`、`source_type`（以上 keyword）、`seq`（integer）、`text`（text）、`locator`（只存储、不索引） |

- 两个索引都是 `dynamic: strict`：写入契约以外的字段直接报错，不会被悄悄加进 mapping。
- 都是 1 个分片、0 个副本（单节点）。相似度显式写成 BM25，`k1=1.2`、`b=0.75`（与 OpenSearch 默认值相同；写出来是为了让实验参数可查、可改）。
- 索引里不放任何权限字段（A10）：谁能看到哪个文档只由数据库决定。

**分词器。**

- 字段引用项目自己起的分词器名 `docmgr_text`。它目前定义为 `{"type": "smartcn"}`，即直接使用 analysis-smartcn 插件自带的 smartcn 分析器（中文分词 + 英文词干 + 停用词），不改它的组成。这样只依赖 `smartcn` 这一个名字；最初的写法是把它拆成 `smartcn_tokenizer` + `porter_stem` + `smartcn_stop` 三部分，复核时因为要多依赖两个名字而改掉。
- 换分词方案只改两个 mapping 文件，但必须删除旧索引、重新创建、再把全部文档重新索引（GLOBAL §11.2）。重建入口是一致性检查的 `repair --fix rebuild-indices`（D31）。
- `ensure_indices` 只创建不存在的索引，不会修改已存在的索引。两个进程同时创建时，后一个收到“已存在”按成功处理。

**写入与删除。**

- `index_document`：先删除这个文档**其他** `parse_version` 的片段，再按 500 条一批写入，`_id` 为 `chunk_id`，同一片段重复写入是覆盖。同一版本的已有片段不删，因为正文片段和之后的 OCR 片段共用版本号、分两次写入。
- `index_doc_meta`：按 `document_id` 整体覆盖文件名和标签。
- `delete_document`：删除这个文档在两个索引里的全部数据；本来就不在索引里时什么也不做。
- 所有写入默认 `refresh=true`：写完立即可搜到，删完立即搜不到。代价是写入较慢，毕设规模可以接受；批量重建时可以传 `refresh=False`。

**错误。**

- `TextIndexUnavailable`（可重试）：连不上、超时、5xx、429，以及按条件删除时部分失败或遇到并发修改。
- `TextIndexError`（不可重试）：其余 4xx、批量写入中有单条被拒。
- 错误信息不包含服务地址。Worker 按异常的 `retryable` 属性决定是否重试（D16）；检索接口（T15）遇到两类错误都必须报告检索服务故障，不能返回空结果（GLOBAL §12）。

**代价与局限。**

- 同一 `parse_version` 下如果片段数变少，多出来的旧片段不会被删掉。按 T12 的确定性切分，同一版本的输入相同、输出相同，正常不会发生。
- 先删旧版本、再写新版本之间如果写入失败，这个文档会暂时没有可检索的片段，靠任务重试恢复。
- 按条件删除只能删到已经刷新过的数据。用 `refresh=False` 写入后马上删除，刚写的数据可能删不掉。默认的 `refresh=true` 没有这个问题；T18 的重建（D31）一律用 `refresh=true`。
- smartcn 分析器类型、在 index 设置里改写默认相似度为 BM25、strict mapping 的写法都没有被任何 OpenSearch 接受过。只要有一处不被 2.19.1 接受，创建索引就会整体失败。
- mapping 是包内的 JSON 数据文件，已在 `backend/pyproject.toml` 的 `[tool.setuptools.package-data]` 里声明。但只验证过可编辑安装（`pip install -e`）能读到，没有做过普通安装来确认文件真的被打包进去。

### D27 解析流水线：parse 与 cleanup 任务、文档状态规则（T14）

代码由“T11 实施 (fork)”会话编写，复核、测试、文档和提交由本会话完成。**涉及数据库和 OpenSearch 的部分都没有实际运行过**，见 `docs/untested.md`。

**文档状态只跟随 parse 任务。**

| 时机 | 文档状态 | 在哪里写 |
|---|---|---|
| 上传成功 | `pending` | 上传接口（T08） |
| parse 任务开始处理 | `processing` | parse 处理函数 |
| parse 成功 | `succeeded`，同时写入 `parse_version` | parse 处理函数，最后一步 |
| parse 任务最终失败（不可重试的错误，或重试次数用完，或租约过期被回收且次数已用完） | `failed` | `shared/tasks.py` 的 `fail` / `reclaim_expired`，与任务状态在同一个事务里更新；只改 `pending` / `processing` 的文档，不覆盖 `succeeded` |
| parse 任务失败但还会重试 | 保持 `processing` | — |
| 重试一个 failed 的 parse 任务 | 从 `failed` 回到 `pending` | 重试接口（`documents/tasks.py` 的 `retry_task`） |

- ocr、cleanup 任务的成败不改变文档状态。OCR 失败时文档仍是 `succeeded`，正文已经可以检索；OCR 的结果要在任务列表里看。T17 如需调整再定。
- “最终失败 → failed”放在任务队列这一层，而不是处理函数里，因为任务超时、Worker 崩溃时处理函数已经不在了，只有“任务被标为 failed”这个动作一定会发生。

**parse 任务的步骤**（`backend/app/worker/handlers/parse.py`，每一步都可以重复执行，结果不变）：

1. 读出文档。记录不存在或已软删除：什么都不做，任务算成功，由 cleanup 任务负责清理。
2. 文档状态改为 `processing`，提交。
3. 确保两个索引存在，然后把文件名和标签写入 `doc_meta`。放在解析之前，即使正文解析失败，文件也能按文件名搜到。
4. 按上传时识别出的真实类型（`mime_type`）选解析器，再切分。PDF 的 `pdf_ocr_min_chars` 算进 parse_version；zip 和像素上限只决定“解析还是拒绝”，不改变解析结果，不算进去。
5. 数据库：删掉这个文档的正文片段和其他版本的全部片段（同一版本的 OCR 片段保留），写入新片段；图片另外登记或更新一条 `image_assets`（宽、高、sha256）。提交。
6. `chunks` 索引：写入这一版的片段，同时删掉其他版本的。
7. 再读一次文档。解析期间它被删除了：把刚写进索引的数据撤掉，结束。
8. 状态改为 `succeeded`，记下 parse_version，同时创建 OCR 任务，一起提交。

- `succeeded` 最后写，所以“成功”一定意味着数据库和索引里都已经有正文片段。
- OCR 任务一页（或一张图片）一个，`payload = {parse_version, locator}`，按“同版本同对象”去重。一页失败只重试这一页；上百页的扫描件也不会因为总耗时超过任务超时而整体失败。
- embed 任务（T21）也在第 8 步的同一事务里创建（仅图片），见 D35。

**cleanup 任务**（`handlers/cleanup.py`）：

- 只清理已软删除的文档。文档没有被删除时直接失败（不可重试），宁可失败也不删用户的文件；记录已不存在时什么都不做，算成功。
- 顺序：删两个索引里的数据 → 删文件 → 硬删除数据库记录。数据库记录最后删：前两步失败时记录还在，重试能再找到要删的东西。
- 硬删除依赖数据库的级联删除，片段、图片记录、共享、标签关联和全部任务记录都会一起删掉，包括正在执行的这个 cleanup 任务自己。所以：
  - 硬删除必须是最后一步。之后再做任何事，父进程下一次续租都会发现记录没了，按“租约丢失”终止子进程。
  - 成功的 cleanup 不会留下任务记录，Worker 的日志里只有一条 info：“清理任务已完成，任务记录已随文档一并删除”。

**运行方式。**

- 处理函数运行在 spawn 出来的子进程里，只收到一个 Task。配置、数据库会话、存储、检索客户端都在子进程里自己建立（`backend/app/worker/context.py`），任务结束时关闭。
- 每个任务开始时调用 `ensure_indices`，不依赖“API、Worker、OpenSearch 谁先启动”。API 和 Worker 启动时都没有调用它。
- 存储模块新增 `local_path(storage_key)`：解析库要的是文件路径。路径经过与 `open()` 相同的安全检查，文件不存在时抛同样的错误；调用方只能读取，不得通过这个路径写入、移动或删除。
- 处理函数自己抛的不可重试错误是 `PipelineError`（原始文件不存在、不认识的文件类型、清理一个没删除的文档）。解析器的 `ParseError`、检索服务的两类错误按各自的 `retryable` 处理。

**标签与索引。**

- 改标签接口在数据库提交之后，尽力把文件名和最新标签同步到 `doc_meta`：先确保索引存在，再写入。检索服务不可用时只记一条警告，标签照常保存，接口不报错。
- `deploy/docker-compose.yml` 给 OpenSearch 设置了 `action.auto_create_index: "false"`。往不存在的索引里写数据时，OpenSearch 默认会自动建一个按数据猜字段类型的索引，没有中文分词，也不是 strict；之后 `ensure_indices` 看到索引已存在就不会再管它。关掉以后，两个索引只能按版本库里的 mapping 创建。

**代价与局限。**

- parse 步骤 7 与 8 之间有一个很窄的窗口：如果此时 cleanup 恰好硬删除了文档，步骤 8 的提交会失败；步骤 6 写进 `chunks` 的数据会残留在索引里，parse 任务记录也已被级联删除。检索时的数据库二次校验（A10）保证这些残留不会出现在结果里；一致性检查把它们报告为 `index_orphan`，用 `--fix index` 清理（D31）。
- parse 失败但还会重试时，任务是 `pending`，文档仍显示 `processing`，直到最终成功或失败。
- 重新解析后（parse_version 变了），旧版本留下的 OCR 任务既不删除也不标记，T17 处理 OCR 任务时要先比对版本。
- 改标签时检索服务如果卡住，这次请求最多多等 `OPENSEARCH_TIMEOUT_SECONDS`（默认 10 秒）。
- 上传之后、parse 任务开始之前，按文件名也搜不到这个文件，因为 `doc_meta` 是在 parse 任务里写的。
- 目前没有改文件名的接口；以后如果加，要同步 `doc_meta`。

代码在 `backend/app/modules/search/`（`channels.py`、`rrf.py`、`params.py`、`service.py`、`schemas.py`）和 `backend/app/api/search.py`。

**处理顺序**（GLOBAL §4.4、§4.5）：

1. 校验请求，确定本次生效的通道和参数。
2. `meta`（`doc_meta` 索引，文件名与标签，B0）和 `text`（`chunks` 索引的 BM25，按 `source_type` 过滤，B1/B2）两路分别检索，各自已聚合到 document_id。`text` 用 OpenSearch 的 `collapse`（按 `document_id` 折叠）每个文档只留得分最高的片段，它同时是该文档的命中证据。
3. RRF 融合：分数为 Σ 1/(k + 名次)，只用名次、不用原始分数（BM25 分数与以后的向量相似度量纲不同）。每通道只取前 `SEARCH_CHANNEL_DEPTH` 名。同分时按 document_id 排序，保证同样的输入得到同样的顺序（实验可重复）。各通道的原始名次和原始分数原样保留在结果里。
4. 数据库二次校验：用 `accessible_filter(user)`（D15）只保留未删除且当前用户有权访问的文档，每次都查、不缓存。
5. 截取前 top_k 个：先过滤、后截取，被过滤掉的文档不占名额。
6. 写 SearchLog。

**权限。** 普通用户的两路查询都带上“可访问 document_id 集合”的 `terms` 前置过滤，作用只是召回：避免前 100 名被别人的文档占满、过滤后结果变少。管理员不加这个过滤。权限的保证始终是第 4 步的二次校验（附录 A10）；它同时挡住 D27 所说的索引残留（记录已经不存在的文档）。

**故障。**

- 任何一路出现 `TextIndexError` 或 `TextIndexUnavailable`，整次检索返回 503 `SEARCH_UNAVAILABLE`。这是有意的：两路都依赖 OpenSearch，一路失败说明检索服务有问题，不悄悄只返回另一路的结果（GLOBAL §12）。
- 故障时也写一条检索日志，记录两路各自的状态。日志写失败时回滚并记错误日志，但不掩盖原本的检索故障。返回给客户端的错误信息不含服务地址。
- 索引不存在时（系统刚部署、还没有文档被解析过），查询路径会调用 `ensure_indices` 按项目 mapping 建好索引（这是一次写操作），再查一次；之后得到的空结果才是真实的“没有数据”。不直接把“索引不存在”当成空结果，以免掩盖索引名前缀配错之类的故障。

**图像通道。** T22 之前没有实现。默认关闭（`SEARCH_CHANNEL_IMAGE_ENABLED=false`）。请求里开启它时，它的状态为 `unavailable`、`detail` 为“图像检索尚未实现”，其余通道照常执行；只开图像通道时返回 200 和空列表。（T22 已实现，见 D36。）

**高亮摘要。** `encoder=html`：片段原文先做 HTML 转义，再插入 `<em>`，所以文档里的 `<script>` 之类只会显示成文字。没有可高亮的词时（例如只靠词干匹配），用 `no_match_size` 从片段开头截取；应答里没有 highlight 时，在 Python 端 `html.escape` 后截取。

**配置**（11 项，`backend/app/config.py`，`.env.example` 已同步）：

| 配置项 | 默认值 | 含义 |
|---|---|---|
| `SEARCH_DEFAULT_TOP_K` | 20 | 请求不指定时返回的文件数 |
| `SEARCH_MAX_TOP_K` | 100 | top_k 上限 |
| `SEARCH_MAX_QUERY_CHARS` | 256 | 检索词长度上限（去掉首尾空白后按字符计） |
| `SEARCH_CHANNEL_DEPTH` | 100 | 每通道最多取多少个文件参与 RRF（截断深度），上限 10000 |
| `SEARCH_RRF_K` | 60 | RRF 常数 k |
| `SEARCH_META_FILENAME_WEIGHT` | 1.0 | meta 通道文件名字段的权重 |
| `SEARCH_META_TAGS_WEIGHT` | 1.0 | meta 通道标签字段的权重 |
| `SEARCH_SNIPPET_CHARS` | 150 | 高亮摘要长度（20–2000） |
| `SEARCH_CHANNEL_META_ENABLED` | true | 请求不指定时 meta 通道是否开启 |
| `SEARCH_CHANNEL_TEXT_ENABLED` | true | 同上，text 通道 |
| `SEARCH_CHANNEL_IMAGE_ENABLED` | false | 同上，image 通道 |

约束：`SEARCH_DEFAULT_TOP_K ≤ SEARCH_MAX_TOP_K ≤ SEARCH_CHANNEL_DEPTH`（每个通道至少要取够 top_k 个文件，否则只开一个通道时凑不满），三个通道开关至少开一个；不满足时启动报错。两项权重相同、k=60 取自 RRF 原论文（Cormack 等，2009），都没有本项目的实验依据，属于阶段五的实验参数。

**SearchLog 的结构。**

- `config`：`{top_k, channels, source_types, params}`。`channels` 是本次生效的通道开关，`params` 是上表全部参数。
- `channels`：`{通道名: {status, took_ms, detail, hits}}`，三个通道各一项。
- `results`：`[{document_id, score, channels, evidence_chunk_id}]`，是返回给用户的最终结果（二次校验、截取之后）；`channels` 为该文档在各通道的原始名次和分数。
- 请求校验失败（422）不写日志。

**代价与局限。**

- `terms` 前置过滤：普通用户的可访问集合超过 OpenSearch 的 `index.max_terms_count`（默认 65536）时，查询会被拒绝，整次检索返回 503；请求体也随文档数线性增长（每个 ID 约 40 字节）。毕设规模不会触发。
- 管理员不加前置过滤：已软删除、尚未清理的文档仍在索引里，会占通道前 100 名的位置。二次校验会把它们去掉，但管理员拿到的结果可能少于 top_k。普通用户的可访问集合本身已排除已删除文档，不受影响。
- `fragment_size` 对 OpenSearch 默认的 unified 高亮器只是近似值，实际摘要可能比 `SEARCH_SNIPPET_CHARS` 长。`no_match_size` 截取的片段是否同样经过 HTML 编码，没有在 OpenSearch 上实测（见 `untested.md`）。
- 一路失败即整体 503（例如 meta 成功、text 失败）。
- 两路串行执行，延迟是两次查询之和。T22 加图像通道时再考虑并行。
- 查询路径在索引不存在时会建索引，检索接口因此不是纯只读的。

### D29 前端检索页与预览页、抽取文本接口（T16）

代码：后端 `backend/app/api/document_text.py`；前端 `frontend/src/views/SearchView.vue`、`PreviewView.vue`、`components/PdfViewer.vue`、`api/search.ts`、`utils/snippet.ts`、`utils/locator.ts`。

**抽取文本接口 `GET /api/documents/{id}/text`（api.md §5.6）。**

- 只返回文档当前 `parse_version` 的片段，按 `seq` 排序。数据来自数据库 `document_chunks` 表，不查 OpenSearch，所以检索服务不可用时仍能预览。
- 分页沿用通用的 `PaginationDep`（默认 20，上限 100）；前端每页取 50。可按 `source_type` 过滤。
- `chunk_id` 参数：直接返回这个片段所在的那一页，忽略 `page`。片段不属于当前版本时（文档被重新解析过）回到第 1 页；格式错误或属于别的文档时返回 422。
- 文档还没有解析成功时返回空列表。权限与下载接口相同（可访问即可）。

**检索页（`/search`）。**

- 检索词写进地址栏（`?q=`），刷新页面或从预览页返回后检索词和结果仍在（返回时会重新检索一次）。
- “检索服务不可用”（503 `SEARCH_UNAVAILABLE`）和“没有找到匹配的文件”分开显示，前者明确写“这不是‘没有搜到’”（GLOBAL §12）。
- 本应执行却失败的通道（`status=unavailable`）逐个提示，例如图像通道尚未实现。（T23 起图像通道已实现，提示文字与颜色见 D37。）
- 正文范围可选正文（body）和 OCR 文字（ocr）。
- 每条结果显示文件名、类型、标签、高亮摘要、位置和命中的通道与名次；点击进入预览页，带上命中的页码或片段。

**预览页（`/documents/:id`，附录 A16）。**

- PDF：用 pdf.js 6.5.438 画在 canvas 上，按设备像素比放大以保证清晰。支持翻页、输入页码、缩放 50%–300%。打开时跳到检索命中的页，页码超出范围时夹到有效页。没有文字选择层。传给 pdf.js 的是数据副本，因为 pdf.js 会把传入的 ArrayBuffer 转交给后台线程，原来那份随之失效。离开页面时调用 loadingTask 的 `destroy()` 释放。
- 图片：用 blob URL 原生显示。下载接口需要登录令牌，所以先带令牌取回字节，PDF 也一样。
- Word、Excel：显示抽取出的文本，并提示看不到原始格式。命中片段加底色并滚动到可见位置，检索词标红。滚动在渲染完成后（`nextTick` 再等两帧）瞬时执行。路由加了 `scrollBehavior`，由 vue-router 接管滚动位置。

**位置显示。** 数据里 `para_index` 从 0 开始，界面从 1 开始显示（`para_index` 为 25 显示为“第 26 段”），写在 `utils/locator.ts` 的注释里。Word 只定位到段落（附录 A9）。Excel 显示工作表名和单元格范围，图片显示“图片”。

**打包。** `pdf.worker` 单独输出，约 1.27 MB。pdf.js 主体在预览页的分块里（约 450 KB，gzip 后约 136 KB），只有打开预览页时才加载。主包大小与 T10 相同（约 874 KB，gzip 后约 279 KB）。Vite 提示有分块超过 500 KB。

**新增依赖。** pdfjs-dist 6.5.438，Barry 于 2026-11-15 批准（`downloads.md` #21）。它的可选依赖 @napi-rs/canvas 和 macOS 原生二进制（#22、#23，约 28 MB）随之自动安装。这两个只在 Node.js 里渲染 PDF 时使用；Barry 于 2026-11-15 决定保留（浏览器用不到，不进打包结果）。

**代价与局限。**

- 页面组件没有自动化测试：项目没有组件测试工具，加装需要 Barry 同意。T16 的页面只对着临时模拟接口在浏览器里检查过，没有与真实后端联调。新增的 18 项前端单元测试覆盖接口封装、摘要清洗、位置格式。
- PDF 不能选中文字，也不能在 PDF 页面上高亮关键词，只能跳到命中页。
- 从预览页后退到检索页时，结果会重新检索并回到页面顶部，不恢复之前的滚动位置。
- 浏览器检查时发现：浏览器面板隐藏时 `requestAnimationFrame` 不执行，命中片段要等页面真正显示时才会滚动。这是测试环境的现象，正常使用的浏览器不受影响。

### D30 OCR Worker（T17）

代码：`services/ocr_worker/ocr_worker/`（`config`、`models`、`rendering`、`engine`、`engine_process`、`store`、`pipeline`、`loop`、`__main__`），运行在 ocr 环境（`env_check/.venv-ocr`）。

**Barry 的选择（2026-11-15，在编写会话里）。** 三个问题的回答原样记录：“按原计划做 OCR Worker”“PP-OCRv5 mobile (Recommended)”“沿用 env_check/.venv-ocr (Recommended)”。计划的批准原话是“批准，开始写”。往 ocr 环境安装 psycopg、PyMuPDF 前，Barry 又在本会话里确认了一次（`downloads.md` #24–#26）。至此第 2 节“OCR 模型规格”这一待定项定为 PP-OCRv5 mobile。

**模块移到 shared。** OCR Worker 在 ocr 环境里，不能导入 backend（附录 A4），但它要切分、写 chunks 索引、领取任务、检查存储路径。所以下面四样移到 `shared`，backend 改为从 shared 导入：

- `shared/chunking`（原 `backend/app/modules/chunking`，M7）
- `shared/text_index`（原 `backend/app/modules/text_index`，M8 的索引部分；mapping 文件随之移动，package-data 改在 `shared/pyproject.toml` 声明）
- `shared/task_queue.py`（`PgTaskQueue`，原在 backend 的 `worker/loop.py`，那里保留一行再导出）
- `shared/storage_keys.py`（storage_key 的白名单与路径安全检查，backend 存储模块的 `_resolve_key` 改为调用它）

这样路径安全规则只有一处，切分和写索引的代码也只有一份。shared 因此新增依赖 httpx 0.28.1（三个环境里都已有同一版本）。

**识别子进程常驻。** PaddleOCR 在一个常驻子进程里加载，模型只加载一次，实测 mobile 加载约 11 秒。PDF 页的渲染也在这个子进程里做。一页超时、子进程崩溃、租约丢失时，杀掉子进程，下一个任务前重新启动。主进程只负责领取任务、续约和写数据库与索引。

**渲染。** PDF 页按 200 dpi（`OCR_PDF_DPI`）渲染成图片。按页面尺寸算出的像素数超过 `OCR_MAX_PIXELS`（默认 1 亿）时，在渲染前就拒绝。独立图片统一转成 RGB。

**识别结果。**

- 只使用 PaddleOCR 结果里的 `rec_texts`、`rec_scores`、`rec_polys` 三项，它们一一对应。不用 `dt_polys`，因为它包含识别后被过滤掉的框，与文字对不上。
- `ocr_results` 表没有唯一约束，按“文档 + 识别对象（locator）”先删后插，重复执行结果相同。
- `model_name` 为 `PP-OCRv5_mobile_det+PP-OCRv5_mobile_rec`。`model_version` 为 `paddleocr-<版本>/det-<sha 前 8 位>/rec-<sha 前 8 位>`，当前是 `paddleocr-3.7.0/det-afa1820c/rec-2460da90`。两个 `inference.pdiparams` 的完整 sha256：检测 `afa1820cb16c1fd0dad589d0f8b389139061c1ef6d68019685fd07be997dda5b`，识别 `2460da90875937c94db97eba74ae3d9e5d4c4c57c42f1f41531c09a26bcc771a`（GLOBAL §3.4 要求记录模型文件的 hash）。

**切分。**

- 一页（或一张图片）里的行用换行拼成一个文本块，再按 D25 的规则切分。不能每行一个块：按 D25，PDF 页和图片的块不与其他块合并，那样每行都会成为一个片段。
- 切分参数随任务传递：parse 任务创建 ocr 任务时，把 `CHUNK_MAX_CHARS`、`CHUNK_OVERLAP_CHARS` 写进 `payload.chunking`。这样 OCR 片段与同一 parse_version 的正文片段用的是同一套参数，与 OCR Worker 自己的配置无关。
- 置信度过滤只影响片段：低于 `OCR_MIN_CONFIDENCE` 的行不进入检索，识别结果仍然全部保存。默认 0，即全部保留，阈值是阶段五的实验参数。

**序号。** OCR 片段与正文片段共用 `{document_id}:{parse_version}:{seq}`。正文从 0 连续编号；OCR 从 `OCR_SEQ_BASE = 1,000,000,000` 开始，每个识别对象预留 1000 个：PDF 第 p 页从 1e9 + (p−1)×1000 起，独立图片从 1e9 起。`seq` 是 32 位整数，按此最多容纳约 114 万页。一页切出超过 1000 个片段时报错，不重试。

**一致性（与重新解析、删除的竞争）。**

1. 开始时比较 `payload.parse_version` 与文档当前的版本，不一致（旧版本留下的任务）或文档已删除，就直接成功结束。
2. 保存结果的事务里，先对文档行加共享锁（`FOR SHARE`）再查一次。文档不存在、已删除或版本已变，就什么都不写，任务成功结束。加锁期间文档不会被硬删除，所以也不会出现外键错误。
3. 写索引只写不删（新增 `shared.text_index.write_chunks`；`index_document` 改为调用它，行为不变）。先用 `delete_chunk_range` 删掉这一页预留区间里的旧片段。
4. 写完再查一次：文档被删除了，就撤掉它在索引里的全部数据；被重新解析了，就只撤掉自己写的这个区间，不碰新版本的片段。

**文档状态。** 沿用 D27：OCR 的成败不改变文档状态。

**启动。** 下面任何一项有问题，都打印原因并以退出码 1 结束，不进入“假成功”状态：

- 配置缺项或不合法；
- 模型目录不存在，提示“本程序不会自动下载模型”；
- 模型加载失败或超时；
- 数据库连不上（加载模型后 `ping` 一次）。

运行中数据库中断时不退出，按轮询间隔重试并记日志。不联网、不下载：两个模型都显式指定 `model_dir`，文档方向分类、文档矫正、文本行方向分类三个可选子模型关闭（它们没有本地目录，开着就会触发下载），并以 `PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK` 作为保险。

与 backend 通用 Worker 的差异：通用 Worker 启动时不检查数据库，连不上时在领取循环里按轮询间隔无限重试，只记日志、不退出。两者在运行中断时的行为相同，只有启动时不同。

**配置（`services/ocr_worker/ocr_worker/config.py`，读项目根目录的 `.env`，环境变量优先）。** `OCR_DET_MODEL_DIR`、`OCR_REC_MODEL_DIR`（默认 `models/ocr/` 下的两个目录）、`OCR_DEVICE`（cpu）、`OCR_PDF_DPI`（200）、`OCR_MIN_CONFIDENCE`（0）、`OCR_MAX_PIXELS`（1 亿）、`OCR_WORKER_LEASE_SECONDS`（60）、`OCR_WORKER_HEARTBEAT_SECONDS`（15，不超过租约的一半）、`OCR_WORKER_POLL_SECONDS`（2）、`OCR_WORKER_TASK_TIMEOUT_SECONDS`（300）、`OCR_WORKER_LOAD_TIMEOUT_SECONDS`（180）、`OCR_WORKER_MEMORY_LIMIT_MB`（3072）、`OCR_WORKER_MAX_TASKS`（200）。

**代价与局限。**

- 文本预览接口按 `seq` 排序，所以扫描页的 OCR 片段排在全部正文片段之后，不按页码穿插。
- 行的顺序按 PaddleOCR 的输出，多栏排版可能错序。
- 真实识别只在 3 种现场生成的图上验证过（扫描版 PDF 页、独立图片、空白图片），没有用真实扫描件或手机照片试过。
- 子进程的内存上限在 macOS 上不生效（D16），启动时会打印“无法设置识别子进程的内存上限”，只受超时保护。
- 识别子进程常驻，约占 1 GB 内存（T00 实测峰值约 1.0 GB）。
- 单个 Worker 串行处理，没有并发。

### D31 一致性检查（T18）

代码：`backend/app/modules/consistency/`（`model`、`collect`、`analyze`、`repair`、`__main__`）。在 `backend/` 目录下用 main 环境运行：`python -m app.modules.consistency check` 或 `python -m app.modules.consistency repair --fix <类别> [--yes]`。

**原则。**

- 以数据库为准（架构原则 3、D9）：磁盘文件和两个索引都按数据库对账，修复也都朝数据库的方向修。
- `check` 只读，不修改任何东西。
- `repair` 必须用 `--fix` 列出要修的类别，没有“全部修复”的选项；不加 `--yes` 时只演练，打印将要做什么，不实际执行。
- 每个修复动作执行前都会再查一次数据库，状态变了就跳过并说明原因。

**修复类别（7 个）。**

| 类别 | 做什么 |
|---|---|
| `index` | 按数据库重建单个文档在两个索引里的数据；已删除或不存在的文档则撤掉它的索引残留 |
| `db-chunks` | 删除数据库里不属于文档当前解析版本的片段 |
| `ocr-results` | 逐条复查后，删除不属于当前版本任何 OCR 对象的识别结果 |
| `cleanup-tasks` | 为“已删除但没有清理任务”的文档补建 cleanup 任务（已有进行中的就不补） |
| `temp-files` | 删除过期的上传临时文件（`.tmp/*.part`） |
| `orphan-files` | 删除数据库里没有记录的已存储文件（删除前再确认一次没有记录） |
| `rebuild-indices` | 删掉两个索引，按版本库里的 mapping 重新创建，再从数据库把全部未删除的文档重新索引 |

**检测项（19 种）。**

| 检测项 | 含义 | 修复类别 |
|---|---|---|
| `missing_file` | 数据库有记录，文件不在磁盘上 | 不能自动修复（数据库是唯一来源，但文件内容只在磁盘上） |
| `orphan_file` | 磁盘上有合法形状的文件，数据库里没有记录（D17 的窗口） | `orphan-files` |
| `stale_temp_file` | 上传临时文件残留（进程被强杀，T05） | `temp-files` |
| `unknown_file` | 存储目录里既不是合法 key、也不是临时文件的东西（含符号链接） | 只报告 |
| `deleted_without_cleanup` | 已软删除，但没有进行中的 cleanup 任务 | `cleanup-tasks` |
| `db_stale_chunks` | 数据库里有不属于当前版本的片段 | `db-chunks` |
| `ocr_result_stale` | 识别结果不属于当前版本的任何 OCR 对象 | `ocr-results` |
| `ocr_chunks_without_result` | 有 OCR 片段但没有对应的识别结果 | 只报告（重新执行该页的 ocr 任务即可） |
| `index_missing` | 索引不存在 | `rebuild-indices` |
| `index_structure_mismatch` | 索引的 mapping 或设置与版本库不一致 | `rebuild-indices` |
| `index_orphan` | 索引里有数据库中不存在的文档（D27 的竞争残留） | `index` |
| `index_deleted` | 索引里有已删除、且没有进行中清理任务的文档 | `index` |
| `doc_meta_missing` | 已解析或解析失败的文档不在 `doc_meta` 里（2026-11-17 起包含解析失败的，见 D34） | `index` |
| `doc_meta_outdated` | `doc_meta` 的文件名或标签与数据库不同（改标签时检索服务不可用） | `index` |
| `chunks_missing_in_index` | 数据库里的片段不在 `chunks` 索引里 | `index` |
| `chunks_extra_in_index` | 索引里有数据库中没有的片段 | `index` |
| `status_without_task` | 状态是等待处理或处理中，但没有进行中的任务 | 只报告 |
| `status_mismatch` | 状态是成功，但没有解析版本 | 只报告 |
| `image_asset_missing` | 已成功处理的图片文档没有 `image_assets` 记录 | 只报告 |

**不报告的情况。**

- 存在时间不到 `--min-age`（默认 3600 秒）的无记录文件和临时文件：上传在“文件已移动、数据库未提交”之间（D17）时，文件暂时没有记录，属于正常状态。
- 已删除、且有进行中 cleanup 任务的文档：它的文件、片段和索引数据马上会被清理掉。
- 有 pending 或 processing 状态的 parse、ocr 任务的文档（`busy`），跳过片段类和索引类检查（`db_stale_chunks`、`ocr_result_stale`、`ocr_chunks_without_result`、`doc_meta` 与 `chunks` 的索引检查）。修复时 `db-chunks`、`ocr-results`、`index` 也会再查一次，遇到这类文档就跳过。理由是 D27 的步骤顺序：parse 在第 5 步就提交了新版本的片段，到第 8 步才把 `parse_version` 改成新版本。在这之间，新片段看起来像“旧版本残留”。首轮复核时发现，如果不跳过，`repair --fix db-chunks` 会删掉正在解析的新片段，parse 随后仍标为成功，文档就失去全部内容；单个文档的索引重建也会冲掉 parse 刚写入的数据。OCR 先写数据库、再写索引（D30），中间也会短暂不一致。

**重建。**

- 单个文档和全部重建都从数据库读当前版本的片段，写入时用 `refresh=true`（D26：未刷新的数据删不掉）。顺序是删除该文档的全部索引数据，再写片段，最后写 `doc_meta`。没有解析版本的文档没有片段可写，但 `doc_meta` 照样写（D34）。
- `rebuild-indices` 就是 D26 要求的重建入口，更换 mapping 或分词器后使用。执行前必须先停掉通用 Worker 和 OCR Worker：重建会删除索引，而 compose 设了 `action.auto_create_index=false`（D27），Worker 这时写索引会失败。帮助文字、演练输出都有这条提示。重建期间检索结果不完整。

**索引扫描与结构检查。** 两个索引分别按 keyword 字段分页读出（`doc_meta` 按 `document_id`，`chunks` 按 `chunk_id`，用 `search_after`）。结构检查用 `GET _mapping` 和 `GET _settings` 的结果，与版本库里的 mapping 文件比较字段定义、`dynamic`、分词器类型和 BM25 参数。

**退出码。**

- 0：没有发现问题，或修复已完成。
- 2：发现了问题，或者是演练。
- 1：配置或数据库出错，或检索服务不可用；后一种情况仍会输出数据库和磁盘的检查结果。`repair` 要修 `index` 或 `rebuild-indices` 而检索服务不可用时，其余类别照常修复，退出码也是 1（D34）。

**代价与局限。**

- 检查与修复之间不加锁，靠执行前的复查和 busy 判断避开正在进行的任务；仍有极小的窗口。
- 全量扫描会把两个索引的条目和全部片段读进内存，只适合毕设规模的数据量。
- `image_embeddings` 的对账和清理留给 T21（D10）；T21 已补上，并覆盖向量索引，见 D35。
- `missing_file` 不能自动修复：文件内容只在磁盘上，只能由人决定删除记录还是找回文件。
- `unknown_file` 只报告，不删除。
- 命令需要完整的后端配置（包括 `JWT_SECRET`），因为它和后端共用同一套配置读取；`__main__` 的说明里写明了这一点。

### D32 实验框架 v1（T19）

代码：`backend/app/modules/experiments/`（`dataset`、`metrics`、`config`、`runner`、`environment`、`__main__`）；数据、配置和使用说明在仓库根目录的 `experiments/`（`experiments/README.md`）。

**批准。** 计划由 Barry 在编写会话里批准，原话“批准，开始写”（由编写会话转述）。

**代码与数据分开放。** 代码放在 backend 里，因为实验要直接调用检索编排（`app.modules.search.service.search`）、读取后端配置、写 `experiment_runs` 表。放在仓库根目录另建一个包，要么重复这些代码，要么另装一个包。数据放在 `experiments/`，与 DEVPLAN §2 的仓库结构一致。

**数据格式。**

- `datasets/manifest.csv`：`file_id, path, type, source, notes`，`type` 为 `pdf`、`scanned_pdf`、`docx`、`xlsx`、`image` 之一，`source` 必填（GLOBAL §9.2 第 1 条）。
- `queries.tsv`：`query_id, type, text`，`type` 为 `text`、`visual`、`mixed`（附录 A18）。
- `qrels/*.tsv`：`query_id, file_id, grade`，`grade` 为 0–3 的整数，可以分多个文件逐周补；同一对的等级在不同文件里矛盾时报错。
- 标注用 `file_id`，不用 `document_id`：`document_id` 要上传后才有，重新导入就全部改变；`file_id` 由标注者自己起，标注可以长期保存。导入时生成 `datasets/document_map.csv`（`file_id, document_id, sha256`）把两者对应起来。评测单位仍是文件（附录 A6）。
- 原文件（`datasets/files/`）、`document_map.csv` 和运行结果（`runs/`）不进 Git。

**指标（`metrics.py`，纯函数）。**

- `P@K` = 前 K 名里相关文件数 / K。返回不足 K 个时，分母仍是 K。
- `R@K` = 前 K 名里相关文件数 / 全部相关文件数。
- `nDCG@K` = DCG@K / IDCG@K，增益为 2^g − 1，折损为 log2(名次 + 1)，IDCG 由全部标注按等级从高到低截取前 K 个算出，与 trec_eval 的 `ndcg_cut` 一致。
- 等级大于 0 才算相关；没有标注的文件等级为 0。
- 没有任何相关文件的查询，三项指标都记为空，不参与任何平均，在结果里单独列出。首轮复核时 P@K 曾按 0 计入平均，与另外两项的分母不一致，已改。
- 数据集以外的文件占名次，但永远不相关。
- 延迟的 P50、P95 用最近秩法，不插值，结果一定是某次实测值；重复运行之间的波动报告平均值、总体标准差、最小和最大值。

**分层报告。** `metrics.json` 先按查询类型（文字型、视觉型、混合型）分层，再给总体（附录 A18）。

**对照组。** `experiments/configs/` 下 B0、B1、B2 三个配置。各组之间只能切换四项：通道开关（三个通道都要写明）、`source_types`、`top_k`、K 值（GLOBAL §9.2：不得为某组实验单独写检索代码）。RRF k、截断深度、字段权重等其余检索参数来自 `.env`，每次运行原样记录。`top_k` 不得小于最大的 K，也不得超过 `SEARCH_MAX_TOP_K`。

**每次运行保存什么。** 结果目录为 `experiments/runs/<UTC 时间到微秒>Z_<实验名>_<6 位随机十六进制>/`，在跑查询之前就创建，避免同一秒内两次运行互相覆盖。

- `config.json`：实验配置；检索参数（`SearchParams` 全部字段）；切分与 OCR 触发参数（`CHUNK_MAX_CHARS`、`CHUNK_OVERLAP_CHARS`、`PDF_OCR_MIN_CHARS`）；数据集统计；版本（`CHUNKER_VERSION`、两个 mapping 文件的 sha256、数据集文件的 parse_version 集合、`ocr_results` 里的 OCR 模型名称和版本）；OpenSearch 版本和插件；机器信息（系统、CPU、内存、Python 版本、git 提交号，以及工作区是否有未提交改动）；运行前检查发现的问题；重复次数；开始时间；是否完整。
- `results.jsonl`：每次重复的每条查询一行，包括排名（file_id、document_id、最终分数、各通道原始名次和分数）、耗时、通道状态、不可用的通道、数据集以外的文件数、各项指标；检索失败的查询记录错误信息。
- `metrics.json`：按查询类型分层和总体的平均值、参与平均的查询数、重复运行之间的波动、失败的检索数、延迟 P50/P95。
- `experiment_runs` 表：一行，`config` 和 `metrics` 与上面两个 JSON 相同，`raw_results_path` 为结果目录相对项目根目录的路径。

**运行前检查。** 下面任何一项不满足，就拒绝运行（退出码 1）：

- 数据集文件都已导入、没有被删除、都已处理成功；
- 全库没有 pending 或 processing 的任务；
- 全库没有已删除但还没清理的文档（D28：管理员检索不做前置过滤，这类文档会占名次）；
- 数据集文件的解析版本只有一个；
- 数据集文件当前版本没有失败的 OCR 任务（D34）。

库里另有不属于数据集的未删除文档时不拦截，但会提示，并把数目记进 `config.json` 的 `documents_outside_dataset`（D34）。

加 `--allow-incomplete` 可以跳过检查继续运行，发现的问题会写进 `config.json`，这次运行也标为不完整。

**不完整的运行。** 检索失败（503）或有通道不可用（例如 T22 之前的图像通道），这次运行都标记为不完整，退出码 2，不能当正式数据（GLOBAL §12：故障不能当成空结果）。

**实验账号。** `import` 时自动创建账号 `experiment`，角色是管理员（看得到全部文档），密码随机生成且不保存，所以这个账号无法登录。实验时检索日志照常写，可以按这个账号和正常使用的日志区分开。

**代价与局限。**

- 现在没有任何评测数据，合成数据或测试数据得到的数字不是实验结果。
- `OCR_MIN_CONFIDENCE`、`OCR_PDF_DPI` 属于 OCR Worker 的配置，backend 读不到，没有记录进 `config.json`；只记录了 `ocr_results` 里的模型名称和版本。
- 运行前检查统计的是全库，别人上传的文件正在处理时也会挡住实验。
- K 最大为 `SEARCH_MAX_TOP_K`（默认 100）。
- 运行中途出现数据库错误时，命令以“无法连接数据库”退出，已跑完的查询不会写进 `results.jsonl`。
- 没有 CER 评测，也没有性能实验（T27）。

### D33 CLIP 模型服务（T20）

代码：`services/clip_service/`（`config`、`core`、`models`、`encoder`、`app`、`__main__`）。接口见 `api.md` §9。

**批准。** Barry 于 2026-11-17 在本会话批准计划（“批准，开始写”），并选定“装 FastAPI (Recommended)”“默认 CPU，可配置 (Recommended)”。没有修改附录 A，没有动数据库表和索引结构。

**模型与环境。**

- 模型：Chinese-CLIP ViT-B-16（文本塔 RoBERTa-wwm-ext-base），512 维，预训练权重，只做推理（GLOBAL §5 第 1 条）。
- clip 环境沿用 T00 实测时建的 `env_check/.venv-clip`（与 D30 沿用 ocr 环境的做法相同）。依赖锁定在 `services/clip_service/requirements.txt`。
- 权重文件从 `env_check/models/` 复制到 `models/clip/clip_cn_vit-b-16.pt`（本地复制，没有下载；`models/` 不进 Git）。sha256 为 `5997ef32c50de18f3ac06eb5d746c324a639053c3bed8f2986f97ebb22b2ecde`，与 T00 记录的一致。
- lmdb：cn_clip 1.6.0 声明依赖 `lmdb==1.3.0`，本机装不上，环境里是 3.0.0。已确认本服务导入和推理都正常（17 项真实模型测试通过）；重建环境时 cn_clip 要用 `--no-deps` 安装，写在 requirements.txt 里。§2 留下的这一处到此确认。

**运行设备默认 CPU。** `CLIP_DEVICE` 可选 `cpu`、`mps`、`cuda`，默认 `cpu`。理由：Barry 的 Mac 和 Windows 补测机上都能用同一设置，结果可复现；T00 实测 CPU 查询编码 P50 20.2 ms，对毕设规模够用。选了本机不支持的设备时启动报错，不自动回退——回退会让实验记录的设备与实际不符。

**启动顺序与失败处理（GLOBAL §3.4、§8.2、§12）。** 读配置 → 检查权重文件 → 加载模型并用一条文本自检 → 开始监听。任何一步有问题都以退出码 1 结束，所以服务能连上就代表模型可用。

- 不使用 `cn_clip.load_from_name`：它在文件缺失时会自动下载。改为自己读本地文件再调 `create_model`。
- 读权重用 `torch.load(weights_only=True)`，只读张量，不执行文件里夹带的代码。
- 配置和文件检查放在导入 torch 之前，缺文件时约 1 秒内报错退出。
- `CLIP_MODEL_SHA256` 填了就核对，不一致不启动；不填只记录。

**模型版本。** `model_name` = `ViT-B-16`；`model_version` = `cn_clip-{cn_clip 版本}-{权重 sha256 前 12 位}`，现为 `cn_clip-1.6.0-5997ef32c50d`，不超过 64 个字符（`image_embeddings.model_version` 的长度）。权重或库版本变了，版本字符串就变，T21 按 `(sha256, model_name, model_version)` 去重时不会把旧向量当成新模型的。预处理规则如果改动，目前**不会**反映在版本里，改预处理时要手动处理旧向量（见局限）。

**固定的预处理（GLOBAL §4.3）。**

- 图片：只接受 PNG、JPEG（与上传允许的图片类型一致），按内容判断 → 按 EXIF 方向摆正 → 转 RGB（透明通道直接丢弃）→ cn_clip 自带变换：双三次插值缩放到 224×224（不保持宽高比）、按 CLIP 的均值方差归一化。
- EXIF 摆正是本项目加的一步：手机照片靠 EXIF 记录方向，浏览器显示时会摆正，编码也应当用摆正后的画面。
- 文本：cn_clip 分词器，上下文 52 个 token，超出截断。
- 输出：L2 归一化的 float32 向量。出现非有限值或零向量时报 500，不返回。

**接口取舍。**

- `/encode/image` 的请求体直接是图片字节：不需要 python-multipart，调用方也简单。一次一张；T21 如果需要批量再评估。
- 图片大小分两层限制：字节数边读边数（不信任 `Content-Length`）；像素数在解码前按文件头判断，防止像素炸弹。超过字节上限时把请求体读完再回 413——首轮测试发现提前断开时，调用方看到的是连接中断而不是 413。
- 推理加一把锁，一次只算一个请求。超时由调用方负责（附录 A5，T22 实现）。
- 默认只监听 `127.0.0.1`，没有鉴权。
- 错误格式与后端一致；错误信息和日志都不含输入内容（GLOBAL §7.2）。
- 接口层（`app.py`）不依赖 torch，编码器从外面传入：接口测试用假编码器在 main 环境里跑，真实模型测试在 clip 环境里跑。

**新增配置。** `CLIP_MODEL_PATH`、`CLIP_MODEL_NAME`、`CLIP_MODEL_SHA256`、`CLIP_DEVICE`、`CLIP_HOST`、`CLIP_PORT`、`CLIP_MAX_IMAGE_BYTES`、`CLIP_MAX_IMAGE_PIXELS`、`CLIP_MAX_TEXTS`、`CLIP_MAX_TEXT_CHARS`，全部可选，默认值见 `.env.example`。后端用的 `CLIP_SERVICE_URL` 是另一个变量，端口要与 `CLIP_PORT` 一致。

**实测（2026-11-17，本机，CPU）。** 加载约 1.3 秒；加载并处理过几个请求后进程内存约 1.3 GB（`ps` 的 RSS，单次观察，不是正式性能数据，T27 再测）。

**局限。**

- 只在 macOS、CPU 上运行过。MPS、CUDA、Windows、Linux 都没有测。
- 同一输入向量完全一致只在“同一进程、CPU、同一批次组成”下验证过；同一文本单独编码和放在一批里编码，结果只保证余弦相似度大于 0.9999，不保证逐位相同。不同机器之间是否逐位相同没有验证。
- 预处理规则没有编进 `model_version`。
- 超过字节上限的请求体会被读完再拒绝，占用连接但不占内存；服务只监听本机，没有再加读取总量的硬上限。
- 缩放不保持宽高比（cn_clip 的标准做法），长宽比悬殊的图片会被压扁。
- 没有做请求排队长度限制；并发很多时后到的请求只是等待，由调用方的超时兜底。
- cn_clip 加载模型时会往标准输出打印几行模型配置，没有屏蔽。

### D34 T15–T19 复核修正（2026-11-17）

**T15 检索。**

- 检索服务应答状态码是 200、内容却不是预期结构（不是 JSON、没有 `hits`、命中里没有排序值）时，原来会变成一个没有说明的 500。现在转成 `TextIndexUnavailable`，接口返回 503 并写检索日志（GLOBAL §12）。

**T16 前端。**

- 预览页的关键词高亮（`highlightText`）原来先转义全文再匹配，关键词会匹配到转义产生的实体内部：搜 `amp`、`lt`、`39` 时，文中的 `&`、`<`、`'` 会显示成乱码。改为在原文上匹配、匹配完逐段转义；同时改成不区分大小写（检索本身不区分）。这不是安全问题（原来也只会插入 `<em>`），是显示错误。
- PDF 预览连续翻页或缩放时，两次绘制可能同时使用同一个 canvas，pdf.js 会报错，页面误报“这一页无法显示”；带页码打开时首次也会画两遍。改为每次绘制带序号，先等上一次真正停下，只有最新的一次去画。页码输入框清空时不再尝试绘制。
- 检索页在上一次请求没返回时不再发新的请求（连按回车时两个应答谁后到谁显示）。

**T17 OCR Worker。**

- 识别子进程忽略 SIGINT。在终端按 Ctrl-C 时信号同时发给父子两个进程，父进程的约定是“处理完当前任务后退出”，子进程原来会被打断，正在识别的这一页被记成一次失败。
- `PgStore.save` 的返回类型标注写成了 `None`，实际返回 `bool`，已改。

**T18 一致性检查。**

- `repair --fix index`（或 `rebuild-indices`）在检索服务不可用时，原来会打印“所选类别下没有需要修复的问题”并以 0 退出：索引根本没被检查，却报成了没有问题。现在明确提示索引类别这次没有修复，其余类别照常处理，退出码 1。
- 重建索引（单个文档和全量）原来不给没有解析版本的文档写 `doc_meta`。而 parse 任务特意在解析之前写 `doc_meta`，为的是解析失败的文件仍能按文件名搜到（D27 第 3 步）。结果是全量重建之后，解析失败的文件从文件名检索里消失，检查也不报告。现在重建时一律写 `doc_meta`；`doc_meta_missing` 的检查范围从“有解析版本”扩大到“有解析版本或状态为 failed”。等待解析的文档仍不要求在 `doc_meta` 里，但全量重建会提前把它写进去（之后 parse 任务会覆盖，无害）。

### D35 图片向量与向量索引（T21）

代码：`backend/app/modules/vector_index/`（`index.py`、`mappings/image_vectors.json`）、`backend/app/modules/clip/client.py`、`backend/app/worker/handlers/embed.py`；cleanup 与一致性检查的改动在原模块里。

**embed 任务在哪个进程。** 由通用 Worker（main 环境）领取，登记在 `registry.HANDLERS`。编码在 CLIP 服务进程里做（附录 A4），Worker 只读文件、发 HTTP、写数据库和索引，不需要深度学习框架。

**创建。** parse 任务解析图片成功时，在同一事务里创建（与 OCR 任务同处），`payload = {"image_id": ...}`，按 payload 去重。不按 parse_version 区分：图片内容不变（附录 A15），重新解析不需要重新编码。

**流程。**

1. 读文档，已删除则什么也不做。
2. 取 `ImageAsset`；找不到或不属于该文档 → `PipelineError`（不可重试）。
3. 调 CLIP `/health` 取当前模型（model_name、model_version、dim）；维度不是 512 → `PipelineError`（换模型要重建向量索引）。
4. 在事务里对 sha256 加 `pg_advisory_xact_lock`，再查 `image_embeddings`（sha256 + model_name + model_version）：有就复用；没有才读文件、调 `/encode/image`。编码应答里的模型与 `/health` 不一致 → `ClipUnavailable`（可重试）。
5. `INSERT … ON CONFLICT DO NOTHING`，提交（同时释放锁）。
6. 复查文档未删除 → `ensure_vector_index` → 写索引 → 再复查，若已删除就撤掉刚写的向量。

效果：同一内容只编码一次，并发时也一样（后到的在锁上等待，醒来后查到先到的结果）。文档状态不跟随 embed 任务（D27）：编码失败时文档仍是 `succeeded`，文件名、正文、OCR 照样可搜，失败原因记在任务上。

**CLIP 客户端的失败分类。** 连不上、超时、5xx、429、应答结构不对 → `ClipUnavailable`（可重试）；413、422 及其他 4xx → `ClipRejected`（不可重试）。错误信息不含服务地址。新增配置 `CLIP_ENCODE_TIMEOUT_SECONDS`（默认 60；服务一次只算一个请求，排队的要等前面的算完，所以比单张编码时间宽得多）。

**向量索引结构。** 逻辑名 `image_vectors`，登记在 `shared/text_index/client.py` 的 `IMAGE_VECTORS`，与另两个索引共用 `OPENSEARCH_INDEX_PREFIX`；不在 `INDEX_NAMES` 里，因为它不是文本索引。mapping：1 分片 0 副本，`dynamic: strict`；`image_id`、`document_id`、`sha256`、`model_name`、`model_version` 为 keyword，`vector` 为 `knn_vector`、`dimension` 512。不开 `index.knn`、不配 `method`，不建 HNSW 图（附录 A12）。`_id` = image_id（独立图片就是 document_id），重复写入是覆盖。写入用 `refresh=true`。mapping 文件在 `backend/pyproject.toml` 里声明为 package-data。新增索引不影响已有两个索引，不需要重建它们。

**精确检索 `search_vectors`。** `script_score` + `lang: knn`、`source: knn_score`、`space_type: cosinesimil`，与 `env_check/01_check_opensearch.py` 在 OpenSearch 2.19.1 上实测通过的写法一致。过滤放在 `script_score.query` 里（前置过滤）：model_name、model_version 两个 term，加可访问 document_id 的 terms（管理员传 `None` 不加；空集合直接返回空、不发请求）。排序 `["_score", {"document_id": "asc"}]`，按 document_id 折叠（P4 内嵌图片出现后每个文档只留最相似的一张）。分数取 `hit.sort[0]`，是 1 + 余弦相似度，只用于排名。索引不存在时先建索引、返回空；其他故障照常抛出，不把故障变成空结果；不合法的命中记日志后跳过。返回前的数据库二次校验仍由 M11 负责（附录 A10）。**尚未接入 M11**：图像通道的调用和超时降级属于 T22。

**开发方式。** 代码由主会话编写，复测、浏览器检查、文档和提交由子代理完成。T23 不带 🔒，没有单独的计划批准。没有改后端、接口和数据契约，没有修改附录 A，没有新下载。

**缩略图。**

- 后端没有缩略图接口，下载接口又要带登录令牌，`<img>` 不能直接用接口地址。所以前端把原图取成 Blob，生成 `blob:` 地址给 `<img>`，由浏览器按比例缩小到 96×96 的框里。
- 只给 PNG、JPEG 类型的结果取图（`isImageType`），与结果是哪个通道命中的无关。
- 超过 5 MB（`THUMBNAIL_MAX_BYTES`）的图片不取，显示“图片较大，点击查看”占位；下载失败显示“无法显示”。缩略图只是辅助显示，失败不影响检索结果。
- 按结果名次排队，同时最多 4 个下载（`THUMBNAIL_CONCURRENCY`）。
- 新的一次检索开始、检索失败或离开页面时，释放已生成的全部 `blob:` 地址，并让上一批作废：迟到的下载不再生成地址。
- 点击缩略图与点击文件名一样进入预览页。

**通道标记与命中依据。**

- 命中通道的标签按通道着色：文件名/标签为灰（info），正文为蓝（primary），图像为绿（success）。名次文字不变。
- 只被图像通道命中、证据是图片时，命中依据写“图像语义匹配（CLIP）”，不写“位置：图片”，与 OCR 文字命中（“位置：图片（OCR 文字）”）分开（GLOBAL §4.1、§13）。

**图像通道开关。**

- 检索页新增“图像语义检索（CLIP）”勾选框，默认不勾（与后端默认关闭一致，D36）。
- 勾选状态写进地址栏（`img=1`），刷新或从预览页返回后保持。
- 请求里总是显式发送 `channels.image`（true 或 false），不依赖后端默认值。

**降级提示。** `status=unavailable` 的通道用黄色（warning）提示。图像通道的提示为“图像检索暂时不可用，本次结果只来自文字检索（原因：…）”，其余通道沿用“××通道未参与本次检索：…”。

**代价与局限。**

- 取的是原图，结果里图片多、图片大时比较费流量和内存；5 MB 上限与并发 4 都没有实验依据。专门的后端缩略图接口记在 DEVPLAN §4（需要 Pillow 之类的图像库，属于新依赖，须 Barry 批准）。
- 只在临时模拟后端上做过浏览器检查，没有与真实后端和真实 CLIP 服务联调；页面组件没有自动化测试（见 `untested.md` T23）。
- `npm run build` 的“chunk 大于 500 kB”警告在 T23 之前就有（主包约 874 kB，来自 Element Plus 等），不是 T23 引入的。
