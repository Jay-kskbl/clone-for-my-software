## 1. 问题

空库（没运行过 `alembic upgrade head`）或没升级到最新迁移的库，Worker 照样启动；要到第一次领取任务、或第一次写 `ocr_results.params` 这样的新列时才报错，而且报的是 SQL 错误。T24c 加迁移 0002 时就碰到过这种风险。

## 2. 逐文件修改记录

| 文件 | 修改 | 原因 |
|---|---|---|
| `backend/app/worker/schema.py`（新增） | `expected_heads()`：读 `app/db/migrations` 得到最新版本（不连数据库）；`schema_problem(conn, heads)`：查 `alembic_version`，表不存在报“还没有建表”，版本不一致报两边的版本和处理办法；`check_schema(url, connect_timeout_seconds=…)`：单独连一次、用完即关 | 迁移版本是唯一可靠的判断依据 |
| `backend/app/worker/__main__.py` | `queue.ping()` 之后调用 `check_schema`（同一个 try：检查中途的数据库错误按“无法连接”处理）；有问题时打印“Worker 无法启动：…”，退出码 1；模块说明的退出码一节补上这种情况 | 与连不上数据库同样处理：重新拉起也没用 |
| `services/ocr_worker/ocr_worker/store.py` | 新增 `REQUIRED_COLUMNS`（OCR Worker 读写的 4 张表的列，取自本文件和 `shared/tasks.py` 的 SQL）、`missing_columns()`、`PgStore.schema_problems()`（查 `information_schema.columns`）；`Store` 协议加上这个方法 | ocr 环境没有 alembic，也不应该依赖 backend 的迁移脚本，只能检查需要的列在不在 |
| `services/ocr_worker/ocr_worker/__main__.py` | `store.ping()` 之后调用 `schema_problems()`；缺列时关闭识别子进程和连接，打印缺几列、列出前 5 个，提示运行 `alembic upgrade head`，退出码 1 | — |

## 5. 修改建议（后续）

1. OCR Worker 的 `REQUIRED_COLUMNS` 要和它的 SQL 一起维护。`test_required_columns_exist_in_the_backend_models` 只保证“列表里的列都存在”，不保证“SQL 用到的列都在列表里”；以后改 OCR Worker 或 `shared/tasks.py` 的 SQL 时要同步。
2. API 进程和命令行工具没有这个检查；API 在空库上启动，到第一个请求才报错。如有需要另立任务。
