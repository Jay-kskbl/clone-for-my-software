- 来源：Barry 要求“从 Windows 测试完成程度去确认软件代码有没有什么需要修改的部分”
- 任务性质：只读分析，没有改任何代码、配置、表结构；要改的都等 Barry 决定后另排任务
- 依据：`output/windows-w4` 至 `w8`、`windows-w3-supplement` 的原始数据和日志（核对见 `windows-2026-11-23-核对.md`），以及对应的代码
- 修改者：Claude（Opus 5.5）

## 1. 建议修改的（按优先级）

### R1 Worker 被强制结束后，它的子进程会变成孤儿，继续把任务跑完（中）——已由 T24ab 修复（D53）

- **证据：** W6 12.5 强制结束通用 Worker（PID 6728）后，`workers-w6/backend2.err.log` 里它的子进程照常跑完任务 `17a34b97`，最后往断开的管道写结果，报 `BrokenPipeError`（`runner.py` 的 `conn.send(None)`）；OCR Worker 同样，`ocr1.err.log`、`ocr2.err.log` 里识别子进程跑完后在 `conn.send(("ok", …))` 报错。
- **原因：** `multiprocessing` 的 `daemon=True` 子进程只在父进程**正常退出**时才会被结束；父进程被 `Stop-Process -Force`、`kill -9`、断电恢复前的系统强杀时，子进程照常运行。这在 Windows、macOS、Linux 上都一样。
- **影响：** 孤儿子进程没有父进程监督，**超时和续租都不再起作用**。租约到期后任务会被另一个 Worker 重新领取，这时孤儿和新的 Worker 可能同时写同一个文档。靠确定性 ID 和“先删后写”，最后结果是对的（W6 12.5 的 SQL 也没有重复），但 OCR 任务建立处（`_create_ocr_tasks`）“先查有没有、再插入”之间没有锁，两边同时跑时有可能建出重复任务。OCR 的识别子进程只做识别、不写库，影响小，只是白占 CPU 和约 3 GB 内存。
- **改法：** 两个子进程入口启动一个看门狗线程，等父进程的 sentinel（`multiprocessing.parent_process().sentinel`，各系统通用），父进程一消失就 `os._exit`。改动约十几行，不涉及表结构、接口、配置。可以写自动化测试（杀掉测试用的父进程，检查孙进程很快退出），在 Mac 上就能跑。
- **性质：** 代码修复，不带 🔒。Windows 上的实测可以并到任务书第 17.5 节（强制结束 Worker，看子进程是否跟着退出）。

### R2 失败的任务没有重试间隔，短暂故障会把重试次数用完（中，要 Barry 定方案）

- **证据 1（OCR）：** 第一轮 W3，51 秒内 8 次崩溃，两个任务 3 次尝试约 40 秒用完，标为 failed，后来手动重试都成功。
- **证据 2（CLIP）：** W8 16.8，CLIP 服务没开时上传图片，embed 任务 14:05:27 建立、14:05:32 已经第 2 次尝试，很快用完 3 次、标为 failed。也就是说，CLIP 服务只停十几秒，这段时间上传的图片就**永久**没有向量，图像检索搜不到；除了逐个点“重试”，没有批量补救的办法，一致性检查也有意不报（`analyze.py`：“还没有向量的图片（embed 任务失败或还没跑）不要求在索引里”）。
- **改法（三选一或组合）：**
  - a. 给任务表加“最早可领取时间”，可重试的失败按 10 秒、60 秒……推迟再领。**要加一列、写迁移 0003，带 🔒**，要先批准方案；
  - b. 加一个命令把失败的 embed 任务放回队列（像 `experiments reocr` 那样），不改表结构；
  - c. 一致性检查新增一类“图片没有向量”，并提供修复（放回 embed 队列）。
- **建议：** 先做 b 或 c（不动表结构、风险小），a 留给 Barry 决定。完整解决还是要 a。

### R3 `consistency repair` 在检索服务不可用时多打一行误导提示（低）

- **证据：** W6 12.4 第 3 步：先提示“index、rebuild-indices 两类这次不会修复”，紧接着又打印“所选类别下没有需要修复的问题。”（`consistency/__main__.py:147`，退出码 1 是对的）。
- **改法：** `index_skipped` 时改印“其余所选类别没有需要修复的问题”。几行字，加一个单元测试。不带 🔒。

### R4 几处很小的改动（低，可以合成一个任务）

- 通用 Worker 的子进程每个任务打印一次“当前系统不支持设置内存上限”，W3 里打了 1000 次，淹没日志（`runner.py` 的 `_limit_memory`）。可以改成父进程启动时打一次。
- 浏览器请求 `favicon.ico` 得到 404（W5 11.6，`index.html` 没写图标）。加一个小图标即可，答辩演示时控制台干净些。
- 检索页四个开关全关后，地址栏留着上一次的 `ch`（W4，`SearchView.vue` 的 `onSearch` 直接返回）。这是合理还是问题，待 Barry 决定。

### R5 OCR Worker 收到停止信号后返回 0，在循环里会被马上重新拉起（中，2026-11-23 补记）

- **更正：** 本文件第 3 节原来把“两个 Worker 停止后的退出码不同（0 与 130）”列为“功能上没有问题”。**这是错的**：写的时候只看了两处返回值，没有核对调用方。
- **原因：** `CLAUDE.md` 的长期运行写法是 `while true; do … -m ocr_worker || break; done`，`scripts/windows/run_ocr_worker_loop.ps1` 也是退出码 0 就重新拉起、130 才结束。0 的含义是“做满任务数，请重新拉起”。通用 Worker 为此在收到停止信号时返回 130；OCR Worker（`ocr_worker/__main__.py`）返回 0。
- **影响：** 按上面的写法运行时，按 Ctrl+C 或发 SIGTERM，OCR Worker 做完当前任务停下后，可能马上又被循环拉起。由代码得出，没有实际按过。
- **改法：** OCR Worker 收到停止信号时也返回 130，加一个单元测试。几行，不带 🔒。

## 4. 只能记录、无法在这里验证的风险

- **`OCR_WORKER_MEMORY_LIMIT_MB` 默认 3072，在 Linux 上可能太小。** W7 里一个识别子进程的工作集峰值是 3053.7 MB；Linux 上这个限制是用 `RLIMIT_AS` 限制**虚拟地址空间**，通常比工作集大得多，因此在 Linux 上 OCR 很可能因为超过这个值而失败。现在没有 Linux 环境，无法验证，项目也没有在 Linux 上部署的计划（Barry 决定不用 Docker，`docs/untested.md` 已登记 RLIMIT 未在 Linux 验证）。如果以后在 Linux 上部署，要先测这个值。
