## 1. 问题

GLOBAL §12：“数据库连接失败 → 启动时给出清楚错误，不进入假成功状态”。

| 进程 | 修改前的行为 |
|---|---|
| OCR Worker | 启动时 `PgStore.ping()`，连不上就打印原因，退出码 1（D30） |
| 通用 Worker | 启动时不检查。连不上时在领取循环里每 `WORKER_POLL_SECONDS` 秒记一条“领取任务失败（OperationalError）”，然后无限重试；进程一直活着，看起来在运行，实际什么都不做 |

## 2. 逐文件修改记录

### 2.1 `shared/task_queue.py`（+7 行）

| 项目 | 内容 |
|---|---|
| 位置 | `PgTaskQueue` 类，`_connection()` 之后、`reclaim_expired()` 之前 |
| 修改 | 新增方法 `ping()`：`self._connection().execute("SELECT 1")`；连不上时抛出 `psycopg.Error` |
| 原因 | 启动检查需要“只连一下”的入口。放在队列类里，检查和领取用同一个连接，检查通过后不用重连 |
| 为什么放 shared 而不是 backend | `PgTaskQueue` 本来就在 shared，两个 Worker 共用。只是新增方法，原有方法没有改 |
| 影响 | OCR Worker 没有调用它（仍用自己的 `PgStore.ping()`），行为不变。ocr 环境以开发模式安装 shared，会直接看到这个新方法，不需要重装 |
| 连接方式 | 沿用 `_connection()`：`autocommit=True`，`SELECT 1` 不会留下未结束的事务 |

### 2.2 `backend/app/worker/__main__.py`（+29/−6 行）

| # | 位置 | 修改前 | 修改后 | 原因 |
|---|---|---|---|---|
| 1 | 模块说明 | 只写了退出码 130 | 列出全部退出码：0 正常、1 配置或数据库有问题、130 收到停止信号 | 外层循环 `… \|\| break` 依赖退出码，要写清楚 |
| 2 | import | — | `import psycopg` | 捕获 `psycopg.Error` |
| 3 | “没有登记处理函数”的警告 | 在登记信号之后 | 挪到读完配置之后 | 让代码按“检查配置 → 检查数据库 → 接管信号 → 进入循环”的顺序排；行为不变 |
| 4 | 建好队列之后 | 直接进入循环 | `queue.ping()`；任何 `psycopg.Error` 都先 `queue.reset()`，再向 stderr 打印“Worker 无法连接数据库（异常类型），请确认数据库已启动、DATABASE_URL 正确”，`return 1` | 本任务的核心改动 |
| 5 | 错误信息 | — | 只写异常类型名，不写异常文本 | psycopg 的异常文本里有主机、端口，认证失败时还有用户名（和 T24b 是同一类问题）。代价：看不到具体原因 |
| 6 | `signal.signal(...)` 两行 | 在建队列之前 | 挪到数据库检查通过之后 | 检查期间（主机不可达时可能卡一阵）按 Ctrl-C 照常中断，不会被“做完当前任务再退出”的处理拦下 |
| 7 | 领取循环 | — | 没有改 | 启动后数据库短暂中断仍然重试（`loop.py` 原有逻辑），不应让 Worker 退出 |

## 4. 修改建议（后续）

1. **CLAUDE.md 的 Worker 命令说明。** 现在写的是“处理满 `WORKER_MAX_TASKS` 个任务后会退出”，没有提“数据库连不上启动即以退出码 1 结束”（OCR Worker 那一行写了）。改 CLAUDE.md 以前都先问过 Barry，这次没有改，**需要 Barry 同意后补一句**。
2. **启动检查的连接超时。** 现在用的是 libpq 的默认值（不设上限）：端口拒绝会立即报错，主机不可达则可能等一两分钟。可以只给 `ping` 那次连接加 `connect_timeout`（例如 10 秒），但 `PgTaskQueue` 的连接两个 Worker 共用，改的话最好单独评估，不放在本任务里。
3. **OCR Worker 可以改用 `PgTaskQueue.ping()`。** 现在它用 `PgStore.ping()` 检查，效果一样。统一能少一处重复，但会改 OCR Worker 的启动流程，需要在 ocr 环境复测，所以没有顺手做。
4. **启动时不检查表结构。** 库是空的（没跑 `alembic upgrade head`）时，`SELECT 1` 能通过，要到第一次领取才报 `UndefinedTable`，然后进入重试。如果想更早发现，可以在检查里加一句查 `processing_tasks` 表是否存在。这超出了 D39 第 6 项的范围，记作待议。
