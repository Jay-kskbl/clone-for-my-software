## 1. 问题

`GET /health` 不需要登录。T01 起，依赖不可用时每一项的 `detail` 是 `"{异常类型}: {异常消息}"`，例如：

```text
OperationalError: connection to server at "127.0.0.1", port 55432 failed: Connection refused
OperationalError: connection to server at "db.internal" (10.0.0.5), port 5432 failed: FATAL:  password authentication failed for user "docmgr"
ConnectError: [Errno 61] Connection refused        （httpx 的部分异常消息里还带完整 URL）
```

任何人都能从这里看到内部主机名、IP、端口和数据库用户名。

## 2. 逐文件修改记录

### 2.1 `backend/app/api/health.py`（+16/−4 行）

| # | 位置 | 修改前 | 修改后 | 原因 |
|---|---|---|---|---|
| 1 | 模块说明 | 两段 | 加一句：公开接口，不可用时 `detail` 只给异常类型，详细原因只写服务端日志 | 说明约束 |
| 2 | 新函数 `_public_detail(exc)` | — | 一般返回 `type(exc).__name__`；`httpx.HTTPStatusError` 返回 `HTTPStatusError: HTTP <状态码>` | 状态码能区分“服务没开”和“开了但报错”，又不带地址 |
| 3 | `_unavailable()` | `detail = f"{类型}: {消息}"`，同一个字符串既写日志又放进响应 | 日志：`健康检查：<组件> 不可用：<类型>: <消息>`（不变，仍是完整原因）；响应：`_public_detail(exc)` | 核心改动：日志和响应分开 |
| 4 | 三个 `check_*` 函数、`health()` 路由 | — | 没有改 | 返回结构、始终 200、`ok`/`degraded` 规则不变 |

对照：

| 情况 | 修改前的 `detail` | 修改后的 `detail` |
|---|---|---|
| 数据库端口拒绝 | `OperationalError: connection to server at "127.0.0.1", port …` | `OperationalError` |
| 数据库认证失败 | `OperationalError: … password authentication failed for user "docmgr"` | `OperationalError` |
| OpenSearch / CLIP 连不上 | `ConnectError: …` | `ConnectError` |
| CLIP 返回 503 | `HTTPStatusError: Server error '503 …' for url 'http://…:8001/health' …` | `HTTPStatusError: HTTP 503` |

| 正常 | `null` 或 `集群状态为 green/yellow` | 不变 |

## 4. 修改建议（后续）

1. **`/health` 是否还需要公开。** 现在不登录就能看到三个依赖是否可用，这本身也透露了一点部署情况（例如有没有 CLIP 服务）。毕设里保持公开方便演示和排查；如果要更严，可以对未登录请求只返回总的 `status`，三项明细只给管理员。这会改接口契约，需要 Barry 决定，这次没做。
2. **其他接口的错误信息。** 本任务只改了 `/health`。检索接口在 CLIP 不可用时的 `detail` 已经在 T22 处理过（测试 `test_clip_service_down_degrades_to_text_search` 断言不含地址）。其他接口的 500 错误走的是统一的错误处理，建议在 T31 一致性核对时顺带检查一遍“对外的错误信息里有没有内部地址”。
3. **答辩准备。** 现在可以说“公开的健康检查只给异常类型，详细原因只在服务端日志里”。剩下的两个安全项（登录不限次数、没有存储配额）仍写进论文“局限与改进”（D39 第 14 项）。
