## 2. 发现的问题

1. **OCR Worker 在 Windows 上按 Ctrl+C 会打断正在识别的任务（代码问题）。** `engine_process.py` 的等待循环在主线程里调用 `Connection.poll()`。Windows 上这个调用等待时会同时等 Ctrl+C 事件，收到后直接抛 `InterruptedError`（PEP 475 的自动重试不覆盖这条路径），循环没有捕获，于是当前任务被记成一次失败并放回队列，Worker 以退出码 1 结束。D34 的约定是“处理完当前任务后退出”。macOS、Linux 上没有这个现象（那里信号处理函数返回后系统调用会自动重试）。
2. **通用 Worker 按 Ctrl+C 时同样会打断当前任务（代码问题，没有实测过）。** `backend/app/worker/runner.py` 有同样的 `poll()` 等待（Windows 上会抛 `InterruptedError`）；而且通用 Worker 的子进程**没有**忽略 SIGINT（D34 只改了 OCR 的识别子进程），在任何系统上按 Ctrl+C，子进程都会收到 `KeyboardInterrupt`，被 `_child_main` 当作一次可重试的失败报告。结果是正在解析的文件被记一次失败、放回队列。
3. **W6 12.4 第 10 步的判定标准定错了。** 删除再写入会在索引里留下“已删除但未合并”的文档，BM25 统计值会因此不同，排名逐条相同是做不到的。应改为：同一索引状态下连续两次运行完全相同（确定性），与 W3 的指标差在很小的范围内，并用 `docs.deleted` 和合并前后的对比证明原因（第 17.4 节）。
4. **`consistency repair` 在检索服务不可用时多打一行“所选类别下没有需要修复的问题”。** 退出码 1 是对的，前一行也写清了“不会修复”，但这一行与 D34 的意图（不能让人误以为没有问题）相反。很小的改动，要不要改由 Barry 决定。
5. **任务书第 13.2 节、第 16.2 节的内存采样脚本把 OCR 识别子进程归错了组。** 已在核对中按原始数据更正；以后的采样改为按父进程归组（第 17.2 节的新脚本）。
6. **W4 偏差 ②：四个开关全关时地址栏保留上一次的 `ch`。** 这时不发请求，刷新页面会按上一次的开关重查，不会出错。可以看成合理（地址栏记的是“最后一次实际执行的检索”），也可以改成全关时清掉 `ch`。待 Barry 决定，不重测。
7. **16.5 第一组的一次 300 秒超时。** 同一文档第二次只用了 88 秒，原因不明；单个 Worker、CPU 占用约 40%，不像是资源不足。第 17.8 节安排了针对这个文档的重复测试。
8. **W5 11.5 的原方案测不到超时**：这台机器所在的网络会立刻回绝 `10.255.255.1`。第 17.3 节改用本地监听。

## 3. Claude 在 Mac 上完成的分析

**16.6 smartcn 怎么切英文：** 转小写（`Names`、`NAMED` → `name`）；做 Porter 词干化（`names`、`named`、`naming` 都归到 `name`，`company` → `compani`，`diabetes` → `diabet`）；**不去英文停用词**（`what`、`is`、`the` 都保留，只能靠 BM25 的 IDF 压低它们的权重）；标点处一律切开（`U.S.A.` → `u`、`s`、`a`，`$1,234.50` → `1`、`234`、`50`，日期按 `-` 切开）；中英混排时中文按词切、英文同样词干化。OCR 文本里能看到识别错误和片段边界的影响（`Revnolds`、`logistlc`、片段开头的半个词 `oduct`、`ers`）。这些写进论文“局限”一节。

**16.7 B2 漏检 270 条的自动分类**（不依赖人工答案；去掉英文虚词和 what / document / title / name / mentioned 这类模板词后，看查询里剩下的词——按前 5 个字母匹配，近似词干——是否出现在相关文档的 OCR 文本里）：

| 类别 | 条数 | 例子 |
|---|---|---|
| A 查询太泛（去掉模板词后没有内容词） | 14 | What is the title of the document? |
| B 内容词都在 OCR 文本里（排名问题） | 33 | What is the name of the meeting? |
| C1 部分内容词不在 OCR 文本里 | 72 | What is the company's name on the letter head? |
| C2 内容词全不在 OCR 文本里 | 151 | What is written in the top right of the document? |

C2 里大量是问版面位置或问法本身的词（top right、signed、fullform），图上本来就没有这些字，所以 C 类**不等于** OCR 认错了。要区分“OCR 漏认”和“图上本来没有”，需要 16.7 B 的 30 条人工答案。结论：DocVQA 是问答数据集，问题不是为检索写的，BM25 漏检主要来自查询和文档用词不重合；这也是不能拿 DocVQA 当正式评测的又一个理由。
