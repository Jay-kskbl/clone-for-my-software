## 1. 问题

W3 的 11 个 `config.json` 记下的三个 mapping SHA-256 与仓库文件不符。把仓库文件换成 CRLF 后重算，三个都吻合：Windows 上 `core.autocrlf=true`，签出时把它们转成了 CRLF。`code_versions()` 对原始字节算 hash，所以同一份 mapping 在两台机器上记下的 hash 不同，实验记录无法据此判断索引结构是否相同。

## 3. 验证（macOS，git 2.50.1，没有安装任何东西）

在 scratchpad 里：从本仓库克隆一个上游，加上新的 `.gitattributes` 做一个临时提交；再用 `git clone --no-checkout -c core.autocrlf=true` 加 sparse-checkout 模拟 Windows 签出。SHA-256 都与主仓库工作区的同名文件比较。验证完已删除 scratchpad 里的全部克隆。

| # | 情形 | `git ls-files --eol` | SHA-256（前 12 位） |
|---|---|---|---|
| A/B | 规则之前签出，然后拉到带规则的提交 | `i/lf w/crlf attr/text eol=lf`；`git status` 为空 | `3f9043ec14c0`、`1588dd184002`、`5d291270ed92`，**正好是 W3 记下的值**，与 Mac 不同 |
| C | 在 B 上执行 `git checkout -- <三个文件>` | 仍是 `w/crlf`（git 认为没有修改，跳过） | 不变 |
| D | 先删掉三个文件，再 `git checkout --` | `i/lf w/lf attr/text eol=lf`；`git status` 为空 | `be91f8071d05`、`0c7937251bab`、`c984e85b889b`，与 Mac 一致 |
| E | 全新克隆（规则已在仓库里） | 三个 `w/lf attr/text eol=lf`；对照文件 `frontend/README.md` 仍是 `w/crlf attr/` | 与 Mac 一致 |
| F | 在 E 上把 `chunks.json` 改成 CRLF（`od -c` 确认是 `\r\n`）再 `git add` | 工作区 `w/crlf`，暂存区 `i/lf`；`git status` 为空 | 暂存区里的内容 `0c7937251bab`，与 Mac 一致（提交端规范化生效） |

另外跑了相关单元测试：backend `tests/unit -k "experiment or environment or mapping or consistency"` 138 passed；shared 108 passed（mapping 内容没变，只是确认没有影响）。

验证时有两次脚本写错（zsh 不按空格拆分变量；在已经是 CRLF 的文件上又加了一次 `\r`），结果作废，按上表重做。

## 4. 修改建议（后续）

1. Windows 执行 W5–W7 前一定要做第 0.2 节第 4 步；漏了的话 W6、W7 的实验记录仍是 CRLF 的 hash，Claude 核对时能看出来（与第一轮的值相同）。
2. 以后如果还有别的文件按原始字节算 hash 记进实验记录，照这个写法加 `text eol=lf`（会手工编辑的）或 `-text`（第三方原样文件，D49）。
3. 第一轮 W3 的结果不需要重跑：内容一致，只是记下的 hash 是 CRLF 版本，核对记录里已经说明。
