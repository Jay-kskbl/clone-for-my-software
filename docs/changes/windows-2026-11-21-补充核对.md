## 2. 核对结果

1. **OCR `0xC0000005`**：`windows-w3-test-evidence.zip` 的 OCR 日志里共 8 次，全部在 14:31:08–14:31:59，4 个 Worker 都有，涉及 4 个文档（`mjbw0217`、`mkvw0217` 3 次都失败；`mkhg0227`、`mjxn0226` 第二次成功）。reocr 时同样 4 个 Worker、同样 500 张图，没有一次崩溃。判断：更像一段时间里的环境故障，不是图片本身的问题；原因未查明。
2. **重试没有间隔**：失败后任务立即回到 `pending`，领取按 `created_at` 排序（`shared/tasks.py`），所以 3 次尝试约 40 秒内用完。改成有间隔要动表结构，属 🔒，未改。
3. **内存**：`memory-peaks.json` 只有 4 个 Python 进程组的峰值（OCR 4910.9 MB 是 4 个 Worker 的合计），没有时间线、系统剩余内存、OpenSearch 和 PostgreSQL，不能判断 14:31 是否内存不足。通用 Worker 日志中“当前系统不支持设置内存上限”出现 1000 次（D16，已知）。
4. **RRF 重算**：7 个融合配置共 210,000 条命中，按 `Σ 1/(k + 通道名次)` 重算，得分不一致 0、顺序错误 0。
5. **B2 与 B3**：B2 前 20 名里找到相关文档的查询 230/500；B2 排第 1 的 132 条到 B3 只剩 43 条，B2 前 10 名里有 119 条在 B3 掉出前 10；逐条比 B3 更好 67 条、更差 175 条。属于 RRF 等权融合的结果，不是程序错误。DocVQA 500 条都是英文文字型查询，只作流程验证。
6. **11-19 记录里的旧失败**（向量分数 2.0 对 1.0、`ConnectionTimeout` 断言）在当前代码中已经修复。
