## 5. 发现的问题

1. **mapping 的 SHA-256 与仓库不一致，原因是 Windows 的换行符。** `config.json` 记录的三个 mapping hash 与 `bba3a1b` 里的文件对不上；把仓库里的文件从 LF 换成 CRLF 后算出的 hash 与记录**完全一致**（doc_meta `3f9043ec…`、chunks `1588dd18…`、image_vectors `5d291270…`）。也就是说 mapping 内容没有问题，但 `code_versions()` 对文件原始字节算 hash，同一份 mapping 在 Windows（`core.autocrlf=true`）和 Mac 上记录的 hash 不同。后果：两台机器的实验记录无法用 mapping hash 判断“索引结构是否相同”。建议（待 Barry 决定）：把 mapping 文件也加进 `.gitattributes`（例如 `shared/text_index/mappings/*.json -text`，或 `eol=lf`），或者改为对解析后的 JSON 算 hash。前者是配置改动，后者是代码改动，都要单独排任务。
2. **`git_dirty: true`。** 11 个目录记录的提交都是 `bba3a1b`（W2 的提交，`8fb5830` 加上 W2 脚本，后端代码没变），但工作区不干净。执行留痕里列了 6 个执行前就存在的未跟踪文件（`deepseek-v4-test.md` 等），`git status --porcelain` 会把未跟踪文件也算进去，这很可能就是原因，但没有当时的输出可以确认。W6 第 12.11 节补交时请一并说明；任务书第 2 节第 11 条已要求以后先保证工作区干净。
3. **`docvqa-runs.zip`（8 MB）被提交进了 Git**，与任务书第 6.5 节不符。已经随合并进入本地历史；是否从仓库删除（删除也只影响之后的提交，历史里仍在）由 Barry 决定。
4. **执行方写的是 `.txt`**（`docs/changes/T24j.txt`、`docs/downloads_DocVQA.txt`），因为 Barry 要求 Windows 上不新建 `.md`。内容尚未并入 `docs/downloads.md`，DocVQA 的下载登记目前只在这份 `.txt` 里。
5. **OCR 两张图片子进程崩溃（`0xC0000005`）**，只有报告里的描述，没有日志；四个 OCR Worker 同时运行时出现、单个 Worker 时重试成功，原因不明。W6 第 12.11 节要求补交日志。
