## 1. CLIP 服务一次只算一个请求，检索可能排在图片编码后面

**改正：** 第一版写的是“批量编码图片时，检索的图像通道会降级”。读完 CLIP 服务的代码、对照 W3 的数据之后，这个风险比第一版说的小得多。

**现状**

- `services/clip_service/clip_service/encoder.py:51` 有一把 `threading.Lock`，只包住模型的前向计算。图片解码和预处理在锁外面（`encoder.py:61-63`）。
- 两个编码接口都在线程池里执行：`/encode/text` 是普通函数（`app.py:105`），`/encode/image` 用 `run_in_threadpool`（`app.py:146`）。不会出现一个请求堵住整个服务的情况。
- 检索编码查询的超时是 3 s（`SEARCH_IMAGE_TIMEOUT_SECONDS`），embed 编码图片的超时是 60 s（`CLIP_ENCODE_TIMEOUT_SECONDS`）。

**机制：** 查询要等的只是排在它前面的前向计算。通用 Worker 一次只处理一个任务，所以一个 Worker 同时最多只有一个 embed 请求在 CLIP 里，检索最多多等一次图片的前向计算。

**数据**

- T00 本机实测（`env_check/env_report.md` §4，CPU）：查询文本编码 P50 20.19 ms；图片编码吞吐 30.9 张/s（batch=8，平均每张约 32 ms；单张编码没有测）。
- W3：6 组开了图像通道的配置，共 9,000 次检索，图像通道降级 0 次。只开图像通道（clip-only）时 P50 96 ms、P95 112 ms、最大 213 ms。

**什么时候才可能超时：** 3 s 相当于几十次前向计算的排队。只有同时开很多个通用 Worker，或者 CPU 被其他进程占满（例如 4 个 OCR Worker 同时识别）时才有可能。`threading.Lock` 不保证先到先得，等的人多时，查询可能被后到的 embed 请求插队。W3 的检索都是在处理完成之后才跑的，“一边处理一边检索”的情况没有数据。

实验已经有保护：运行前检查要求数据集里每张图片都有当前模型的向量（`backend/app/modules/experiments/__main__.py:327`），embed 没跑完时 B3 类配置不会运行。T26 的数字不受这个问题影响。

**可选做法**

| 做法 | 收益 | 代价 |
|---|---|---|
| **A 不改，T27 补测一次（建议）** | 拿到“一边处理一边检索”时的真实延迟 | 一次测量 |
| B 查询编码优先（两把锁或优先队列） | 查询不再排在 embed 后面 | 改 CLIP 服务的并发设计（D33），要补测试；现有数据看不出有这个必要 |
| C 调大查询超时 | 降级更少 | 出故障时用户要等更久；同样没有数据支持 |

**建议：A。** T27 测性能时加一组：OCR Worker 和 embed 任务都在运行时做检索，从 `search_logs.channels` 读图像通道的 `status` 和 `took_ms`。演示时如果 OCR 还在跑，留意检索页上的“图像通道不可用”提示就行。

## 2. 普通用户的可访问文档 ID 全部放进检索请求

**现状**

- 非管理员每次检索时，`backend/app/modules/search/service.py` 的 `_accessible_ids` 先查出全部可访问的 document_id（`backend/app/modules/auth/permissions.py` 的 `accessible_document_ids`）。
- 三个通道各自把这份 ID 作为 `terms` 过滤带上：meta、text 在 `search/channels.py` 的 `_id_filter`，image 在 `vector_index/index.py:151`。管理员不加这个过滤。

**为什么是现在这样：** 这是附录 A12 的权限前置过滤：先过滤，再取每个通道的前 100 名，别人的文档就不会占掉名额。真正保证权限的是返回前的数据库二次校验（附录 A10），前置过滤只是为了召回。

**数据（计算值，没有实测）**

| 可访问文档数 | 每个通道的过滤条件 | 一次检索（三个通道） |
|---|---:|---:|
| 500（毕设数据集规模） | 约 19 KB | 约 57 KB |
| 65,536（OpenSearch 默认上限） | 约 2.4 MB | 约 7.3 MB |

按每个 UUID 在 JSON 里约 39 字节计算。OpenSearch 的 `index.max_terms_count` 默认是 65,536，超过时查询会被拒绝，meta 或 text 通道出错，整次检索返回 503。还没到这个上限，每次检索要发好几 MB 的过滤条件，延迟就会先明显变差。数据库这边每次检索也要查一次全部可访问 ID，`documents.owner_id` 上有索引。

**可选做法**

| 做法 | 收益 | 代价 |
|---|---|---|
| **A 不改，写进局限（建议）** | 无 | 无 |
| B 可访问文档超过某个数量时改成后置过滤，加大截断深度 | 没有上限 | 要改附录 A12；过滤后结果可能变少，这正是 A12 要避免的 |
| C 把 owner 和共享对象写进索引做粗过滤，数据库二次校验保留 | 请求大小和文档数无关 | 每次共享、取消共享都要更新这个文档在三个索引里的全部数据；一致性检查要多比一项；工作量大 |
| D 调大 `index.max_terms_count` | 上限往后推 | 请求照样越来越大；要改索引设置 |

**建议：A，写进论文“局限与改进”。** 可以这样写：权限前置过滤把可访问文档的 ID 放进检索请求，适合单个用户可访问的文档在数千个以内的规模；规模更大时，可以把文档的 owner 和共享对象写进索引做粗过滤，返回前的数据库二次校验保持不变。

## 3. 每个任务新开一个子进程

**现状：** `backend/app/worker/runner.py` 用 spawn 方式为每个任务启动一个新的 Python 解释器。子进程重新导入处理函数所在的模块，在 `backend/app/worker/context.py` 里重新读配置、建数据库引擎和检索客户端，做完一个任务就退出。OCR Worker 不是这样：它的识别子进程常驻，模型只加载一次。

**数据（这次在本机补测）**

| 子进程里做的事 | 耗时（中位数） |
|---|---:|
| 什么都不做（只启动解释器和 runner 模块） | 0.067 s |
| 再导入任务处理模块（和真实任务相同） | 0.347 s |
| 再读配置、建数据库引擎和检索客户端 | 0.364 s |

测法：Apple M4，macOS，主环境，直接调用 `run_in_subprocess`，每项跑 7 次，去掉第一次后取中位数。不连数据库，也不做任务本身的工作，所以这是纯粹的固定开销。导入的时间主要花在解析库和 SQLAlchemy 上。**未测试（Not Tested）：** Windows 上的开销。W3 正是在 Windows 上跑的，那里 spawn 一般更慢。

**影响：** W3 里通用 Worker 处理了 1,000 个任务（parse、embed 各 500）。按本机的数字估算，固定开销合计约 6 分钟。同一时间 OCR 才是关键路径：500 页 × 平均 53.57 s ÷ 4 个 OCR Worker ≈ 1 小时 52 分，占了总时长 2 小时 6 分的大部分。通用 Worker 的开销和 OCR 同时发生，没有拉长总时长。只有数据集以带文字层的 PDF、Word 为主（不需要 OCR）时，parse 才会成为关键路径；即便那样，500 个文件也只多约 3 分钟。

**可选做法**

| 做法 | 收益 | 代价 |
|---|---|---|
| **A 不改（建议）** | 无 | 无 |
| B embed、cleanup 改在 Worker 主进程里执行（它们不解析文件） | 这两类任务每个省约 0.36 s | 处理期间主线程被占住，要另开线程续租；没有子进程就不能在超时时强制结束，只能靠 HTTP 超时；附录 A3 的说明要改 |
| C 子进程复用：一个子进程连续处理多个任务再退出，类似 OCR 的常驻识别子进程 | 导入只做一次，隔离还在 | 任务之间可能残留状态；父子进程之间要来回传任务和结果；崩溃处理要重写；工作量最大 |
| D macOS、Linux 改用 forkserver 并预加载模块 | 子进程几乎不用导入 | Windows 没有 forkserver，三个系统的行为不再一致，这正是当初选 spawn 的理由（`runner.py` 注释） |

**建议：A。** 这 0.36 s 换来的是附录 A3 的隔离：解析库碰到畸形文件卡死、吃光内存或者直接崩溃时，只有这一个任务失败，Worker 和其他文件都不受影响。答辩被问到时，可以用上面的数字说明这个代价在本系统里不在关键路径上。

## 4. meta 和 text 两个文本通道依次执行

**现状：** `backend/app/modules/search/service.py` 的 `_finish` 在请求线程里先查 meta，再查 text；图像通道在另一个线程里同时跑（`ThreadPoolExecutor(max_workers=1)`）。总耗时约等于 max(meta + text, image)，再加上融合、二次校验和写日志。

**数据（W3，每组 500 条查询 × 3 次，单位 ms）**

| 配置 | 开的通道 | P50 | P95 |
|---|---|---:|---:|
| B0 | meta | 2 | 4 |
| B1 | text（只查正文） | 2 | 3 |
| B2 | text（正文 + OCR） | 22 | 31 |
| B3-no-clip | meta + text | 23 | 35 |
| clip-only | image | 96 | 112 |
| B3 | meta + text + image | 100 | 123 |

B1 快是因为 DocVQA 的文件都是图片，没有正文可匹配。

**分析**

- 只开文本类通道时，把 meta 和 text 并行，最多省下 meta 的那 2 ms 左右。
- 开了图像通道时，图像这一路约 96 ms，比 meta + text 的约 23 ms 慢得多，总耗时已经由它决定，并行两个文本通道省 0 ms。
- B3 只比 clip-only 多约 4 ms，说明融合、二次校验和写日志的开销很小。

**可选做法**

| 做法 | 收益 | 代价 |
|---|---|---|
| **A 不改（建议）** | 无 | 无 |
| B meta、text 也各开一个线程 | B2 类请求省约 2 ms，B3 省 0 ms | 错误处理要改：现在靠“当前在查哪个通道”判断 503 出在哪里；要补测试 |

**建议：A。** 真正值得弄清楚的是图像通道那 96 ms 花在哪里：T00 在本机测的查询编码只要 20 ms，剩下的是 Windows 机器上的编码、HTTP 往返，还是向量精确检索，现在分不出来。`search_logs.channels` 记了每个通道的 `took_ms`，但只到通道这一级；要再拆成“编码”和“向量检索”，需要在 `channels.search_image` 里分开计时。这是个小改动，T27 前再决定做不做。

## 5. 每次写索引都立即刷新

**现状：** 所有索引写入默认 `refresh=true`：文本索引在 `shared/text_index/indexer.py` 的 `_refresh`，向量索引在 `backend/app/modules/vector_index/index.py:90、110`。

**为什么是现在这样（D26）**

- 写完立刻能搜到，删完立刻搜不到。
- 更重要的是正确性：按条件删除（`_delete_by_query`）只能删到已经刷新过的数据。parse 先删掉其他版本的片段再写新片段，OCR 重新识别一页时先删掉这一页的旧片段再写，这些“先删后写”都要求之前写进去的数据已经刷新。

**数据（按代码数出来的请求数，没有实测）**

| 任务 | 触发刷新的请求 | 次数 |
|---|---|---:|
| parse（图片） | 写 doc_meta、删除其他版本的片段 | 2 |
| parse（有正文的文档） | 同上，另外每 500 个片段一次批量写入 | 2 + ⌈n/500⌉ |
| ocr（每页） | 删除这一页的旧片段、写入新片段 | 2 |
| embed | 写向量 | 1 |
| cleanup | 删 chunks、删 doc_meta、删向量 | 3 |

W3 每张图片约 5 次，500 张约 2,500 次，分布在约 2 小时里，平均每秒约 0.3 次。对 OpenSearch 来说负担很轻。

**可选做法**

| 做法 | 收益 | 代价 |
|---|---|---|
| **A 不改（建议）** | 无 | 无 |
| B 改用 `refresh=wait_for`（等下一次定时刷新再返回） | 不再强制刷新 | 每次写入最多要等 1 s（默认刷新间隔）。Worker 是一次接一次地写，处理反而变慢；按条件删除也不支持 wait_for |
| C 批量处理时关掉刷新，最后统一刷新一次 | 大批量时减轻 OpenSearch 的负担 | 破坏上面的正确性前提，重试或重新解析时旧片段可能删不掉；还要给 Worker 加一个“批量模式” |

**建议：A。** 这是 D26 写明接受的代价（“写入较慢，毕设规模可以接受”），W3 的数字也支持这个判断。

## 6. 每个任务开头检查索引是否存在

**改正：** 第一版写的是“每次 2 个 HEAD 请求（embed 再加 1 个）”。embed 只检查向量索引，一共是 1 个。

**现状**

| 调用位置 | 检查的索引 | HEAD 请求 |
|---|---|---:|
| `backend/app/worker/handlers/parse.py:254` | doc_meta、chunks | 2 |
| `backend/app/worker/handlers/cleanup.py:40` | doc_meta、chunks | 2 |
| `backend/app/worker/handlers/embed.py:145` | image_vectors | 1 |
| `services/ocr_worker/ocr_worker/pipeline.py:251` | doc_meta、chunks | 2 |
| `backend/app/api/documents.py:227`（改标签） | doc_meta、chunks | 2 |

检索时平时不发 HEAD：只有 OpenSearch 回答“索引不存在”时才去建索引（`search/channels.py:90`、`vector_index/index.py:230`）。

**为什么是现在这样（D27）：** 索引在第一次需要时按项目自己的 mapping 创建，所以检索服务比 Worker 晚启动也没关系。compose 关掉了 OpenSearch 的自动建索引（`action.auto_create_index=false`），往不存在的索引里写数据会直接失败，而不是自动建出一个没有中文分词的索引。

**数据：** W3 约 2,500 个 HEAD 请求（parse、ocr 各 1,000，embed 500）。本机回环上一个 HEAD 一般是毫秒级（没有实测），合计几秒，而且分散在 2 小时里。

**可选做法**

| 做法 | 收益 | 代价 |
|---|---|---|
| **A 保持（建议）** | 无 | 无 |
| B 在进程里记住“已经检查过” | 省掉重复的 HEAD | 通用 Worker 每个任务都是新进程（第 3 项），根本记不住；只有 OCR Worker 用得上，而它每页要 53 s，省下的几毫秒可以忽略；`rebuild-indices` 删掉索引之后，记住的结果还会过期 |

**建议：A，保持现状。**
